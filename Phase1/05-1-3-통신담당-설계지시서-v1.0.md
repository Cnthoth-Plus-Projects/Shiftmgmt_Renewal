## 2. 고정 결정 D1~D10

### D1. 111 계약은 하나의 실행 메타표로 만든다

새 `src/shared/bridge/channel-contracts.ts`에 111행을 `as const`로 둔다. 각 행은 `method`, `channel`, `group`, `guard`, 선택 `actionPermission`, `recordsActivity`, `dialog`, `usesDataDir`를 가진다. 값은 계약표 v0.2에서만 옮긴다.

- `method`는 합성 브라우저 브리지의 키다.
- `channel`은 `/api/<channel>`의 뒤쪽과 정확히 같다.
- `guard`는 `none | session | action | admin | accessHistory` 중 하나다.
- `action`이면 `actionPermission`이 반드시 있고, 나머지는 없어야 한다.
- 테스트가 111, 메서드·채널 중복 0, 분포 40/35/22/1/13, 활동 63, dialog 8, dataDir 27을 고정한다.
- `contracts.ts`는 LOCK 복사본이므로 타입 추가를 위해서도 수정하지 않는다.

### D2. 등록과 실행을 분리한다

`src/main/http/route-registry.ts`가 다음을 소유한다.

1. 채널별 업무 handler 등록. 중복 채널, 메타표에 없는 채널, 슬라이스의 기대 집합 누락은 즉시 throw.
2. 요청마다 메타표의 guard를 먼저 실행.
3. 통과하면 원본과 같은 인수 순서로 handler 호출.
4. handler의 계약 결과는 그대로 반환.

`auth:change-password`는 계약표의 IPC guard 값 `none`과 별개인 **HTTP 전환 예외**다. 브라우저 쿠키가 원본 IPC의 단일 renderer 호출자를 대신하므로 route registry는 이 채널에만 `requireAuthenticatedSession`을 먼저 적용한다. 이것은 operational guard가 아니다. 따라서 `passwordChangeRequired` 세션도 통과해 비밀번호를 바꿀 수 있다. 다른 `guard=none` 채널에는 이 예외를 적용하지 않는다.

업무 파일은 `src/main/http/routes/{core,operations,workforce,performance,allowance}-routes.ts` 다섯 개다. 원본 5개 블록을 서비스 호출·errorCode·활동 세부 문구·호출 순서 단위로 옮긴다. 기회성 리팩터링을 하지 않는다.

### D3. HTTP 상태와 계약 실패를 구분한다

처리 순서는 아래와 같다.

```text
Host -> API 경로/메서드 -> Origin/Sec-Fetch-Site -> Content-Type
-> 최대 크기/JSON parse -> 최상위 배열 -> route guard
-> 원본 service/action -> 성공 활동 기록 -> JSON 응답
```

- 빈 본문, JSON 문법 오류, 최상위가 배열이 아닌 `{}`, `"x"`, `5`, `null`, `true/false`는 HTTP 400 `BAD_REQUEST`다. `[]`로 보정하지 않는다.
- 계약상 실패는 HTTP 200 + 원본 `BridgeFailure`다.
- 세션 없음·만료로 guard가 만든 `AUTH_SESSION_REQUIRED`만 HTTP 401로 보내되 본문은 그 원본 `BridgeFailure`다.
- 비밀번호 변경 필요, 역할·행위 권한 부족은 원본 오류 코드의 계약 실패이므로 HTTP 200이다.
- Origin/Fetch Metadata 403은 통신 경계의 `FORBIDDEN`이고, 업무 권한 실패와 섞지 않는다.
- 예상하지 못한 throw만 HTTP 500 `INTERNAL_ERROR`; 원본 `runIpcAction`이 잡아 만든 실패를 500으로 바꾸지 않는다.
- 110개 응답 외형은 `BridgeResult`; `app:get-version` 하나만 JSON 문자열이다.

### D4. 세션은 원본 단일 세션 + 불투명 쿠키로 연결한다

`src/main/http/session.ts`가 `withSession`, `withActionPermission`, `withAdmin`, `withAccessHistory`, `recordActivity`, `recordSuccessfulActivity`를 같은 이름으로 제공한다.

- 로그인 성공 때 `randomBytes(32).toString("hex")`로 HTTP 세션 id를 발급한다.
- 쿠키는 `sm_session=<id>; HttpOnly; SameSite=Strict; Path=/`다. `AuthSession.sessionToken`을 쿠키 id로 재사용하지 않는다.
- 메모리 `Map<id, { session, issuedAt, lastSeenAt }>`만 사용하고 디스크에 저장하지 않는다.
- 원본 `auth-service.ts`가 단일 `currentSession`이므로 로그인 성공 때 기존 map 항목을 전부 지워 단일 세션 의미를 보존한다.
- 로그인 실패는 기존 유효 map/global session을 지우지 않는다.
- 유효한 쿠키를 찾은 뒤에만 원본 `getSessionWithRenewal()`을 호출해 8시간 갱신을 동기화한다. 없는 쿠키가 원본 전역 세션을 빌려 쓰면 안 된다.
- `auth:get-session`은 원본처럼 갱신하지 않고, 쿠키가 없거나 무효면 `{ ok: true, data: null }`이다.
- `auth:change-password`는 operational guard가 아니라 유효한 인증 세션만 요구한다. 그래야 `passwordChangeRequired` 사용자가 비밀번호를 바꿀 수 있다. 성공 결과로 map의 세션을 갱신한다.
- `auth:sign-out`은 **현재 map에 유효하게 매핑된 쿠키**가 제시됐을 때만 원본 전역 세션과 map을 함께 지우고, `sm_session=; HttpOnly; SameSite=Strict; Path=/; Max-Age=0`로 브라우저 쿠키를 만료시킨다. 쿠키가 없거나 임의·옛 id면 성공 no-op + 그 쿠키만 만료하며, 다른 현재 세션을 로그아웃시키거나 활동 기록을 남기지 않는다.
- 서버 재시작은 map이 비므로 전부 로그아웃이다.
- 활동 기록 실패는 업무 결과를 바꾸지 않고, `result.ok === true`일 때만 1회 기록한다.

### D5. 자동 업데이트 5개는 disabled provider로 계약을 유지한다

Phase 1에서 `app-update-service.ts`를 되살리지 않는다. 대신 core routes 안의 provider가 항상 다음 상태를 만든다.

```json
{
  "enabled": false,
  "status": "idle",
  "currentVersion": "<VERSION>",
  "availableManifest": null,
  "releaseNotesToShow": null
}
```

`app:get-update-state`, `app:check-for-update`, `app:download-update`, `app:install-update`, `app:dismiss-update-notice`는 원본 서비스의 `enabled === false` 경로처럼 이 상태를 성공 `BridgeResult`로 돌려준다. 새 업데이트 failure나 가짜 진행 상태를 만들지 않는다. 원본 core handler의 성공 활동 기록 조건은 그대로 적용한다.

disabled 상태의 활동 기록 기대값도 고정한다. `app:check-for-update` 성공은 원본처럼 `app-update-check` / `최신 버전 확인`을 1회 기록한다. `app:get-update-state`는 기록 0회다. `app:download-update`·`app:install-update`는 `targetVersion`이 없고 `app:dismiss-update-notice`는 `releaseNotesToShow`가 없으므로 각각 기록 0회다.

### D7. Windows 대화상자 실행기는 하나다

`scripts/windows-dialog.ps1` + `src/main/http/dialog-bridge.ts`를 사용한다. 실측 런타임은 Windows PowerShell `5.1.26100.9444`, `FolderBrowserDialog` 속성은 `Description`, `SelectedPath`, `ShowNewFolderButton` 등이며 `Title`은 없다. 폴더 선택은 승인된 `System.Windows.Forms.FolderBrowserDialog` 구형 트리 창으로 고정한다.

Node -> PowerShell stdin JSON:

```json
{
  "operation": "openFile | openFolder | saveFile | openPath",
  "title": "string?",
  "defaultPath": "string?",
  "filters": [{ "name": "string", "extensions": ["xlsx"] }],
  "showOverwriteConfirmation": true,
  "path": "openPath에서만"
}
```

PowerShell -> Node stdout 한 줄 JSON:

```json
{ "ok": true, "cancelled": false, "path": "C:\\..." }
{ "ok": true, "cancelled": true }
```

규칙:

- `scriptPath = path.join(resolveRepoRoot(), "scripts", "windows-dialog.ps1")`로 절대 경로를 만든 뒤 `spawn("powershell.exe", ["-NoLogo", "-NoProfile", "-NonInteractive", "-STA", "-ExecutionPolicy", "Bypass", "-File", scriptPath])`와 같은 인수 배열로 실행한다. 실행할 스크립트 파일은 이 하나뿐이다.
- 경로·제목·필터는 명령 문자열에 보간하지 않고 UTF-8 JSON stdin으로 한 번만 전달한다. `Invoke-Expression` 금지.
- stdout은 BOM 없는 UTF-8 JSON 한 줄만, stderr는 진단 전용. nonzero, JSON 파싱 실패, schema 불일치, stdout 잡음은 호출 채널의 기존 errorCode `BridgeFailure`로 변환한다.
- Node는 `Buffer.from(JSON.stringify(request), "utf8")`를 stdin에 쓰고 닫는다. ps1은 시작 시 `UTF8Encoding(false)`를 만들고 `Console.OpenStandardInput()`의 `StreamReader`로 stdin 전체를 한 번 읽으며, 같은 encoding을 `Console.OutputEncoding`과 `Console.OpenStandardOutput()`의 `StreamWriter`에 명시한다. `ConvertTo-Json -Compress` 결과만 `WriteLine`으로 정확히 한 줄 쓴다. Windows PowerShell 5.1 기본 인코딩에 맡기지 않는다.
- 하나의 전역 FIFO가 open/save/openPath를 모두 직렬화한다. queued 요청이 취소되면 spawn하지 않는다. active 요청 abort·서버 종료 때 child를 종료하고 종료를 기다린 뒤 다음 요청을 처리한다.
- `FolderBrowserDialog.title`은 `Description`, `buttonLabel`은 받되 무시, `ShowNewFolderButton = true`다.
- Open/Save dialog는 `title`, `defaultPath`, `filters`, save overwrite 확인을 대응한다. defaultPath가 파일이면 부모를 InitialDirectory, basename을 FileName으로 나눈다.
- 보이지 않는 TopMost `Form`을 owner로 쓰고 모든 dialog/form을 `finally`에서 Dispose한다.
- `Start-Process`는 `Start-Process -FilePath $request.path -ErrorAction Stop`처럼 변수 인수로 호출한다.
- stdout/stderr는 각각 64 KiB를 넘으면 child를 종료하고 실패한다. 고정 timeout은 두지 않는다.

### D8. 브라우저 브리지는 메타표에서 합성한다

`src/web/bridge/app-bridge.ts`는 `AppBridge & AuthBridge & AccessLogBridge & WorkforceBridge & OperationsBridge & DashboardBridge & PerformanceBridge & AllowanceBridge`를 `BrowserAppBridge`로 정의한다.

- 111 메서드를 손으로 다시 열거하지 않고 D1의 `method -> channel` 표에서 합성한다.
- 호출 인수 배열의 **뒤쪽 `undefined`만** 제거한다. 원본 배열을 mutate하지 않는다.
- `fetch('/api/' + channel, { method:'POST', credentials:'same-origin', headers:{'Content-Type':'application/json'}, body: JSON.stringify(args) })`.
- 정상 메서드의 응답 외형은 성공이면 object + `ok:true` + own `data`, 실패면 `ok:false` + string `errorCode` + string `message`까지 검사한다.
- non-2xx라도 유효한 `BridgeFailure`면 그대로 반환한다.
- network 실패는 정상 메서드에서 `NETWORK_ERROR`; JSON/외형 오류는 `INVALID_RESPONSE`.
- `getAppVersion`은 JSON string만 허용한다. 네트워크·상태·JSON·형태 오류는 `""`나 `BridgeFailure`로 바꾸지 않고 Promise reject한다.
- `window.appBridge` 설치는 한 번이며, `src/web/app.ts`가 side-effect import한다.

### D9. 서버 수명은 서비스 수명과 함께 간다

공개 진입점 소유권은 다음처럼 하나로 고정한다.

- `src/main/server.ts`는 기존 `createServer(options): Server`, `startServer(options): Server`, direct-execution 검사, SIGINT/SIGTERM 등록의 **유일한 소유자**로 남는다. 다른 파일은 process signal을 등록하거나 `process.exit`를 부르지 않는다.
- `src/main/runtime.ts`는 주입 가능한 `initialize()`, `startBackground()`, `shutdownOnce()` lifecycle만 소유한다. `shutdownOnce()`는 첫 호출의 Promise를 저장해 동시·반복 호출이 같은 Promise를 받고 모든 자원을 정확히 한 번만 정리하게 한다.
- `createServer()` 자체는 DB 초기화·timer·signal 등록이 없는 side-effect-free 조립 함수다. production lifecycle은 `startServer()`만 시작한다.
- composition root인 `server.ts`가 repo root와 `scripts/windows-dialog.ps1` 절대 경로를 계산해 dialog bridge에 주입한다. dialog bridge가 `server.ts`를 import하는 순환 의존을 만들지 않는다.
- signal handler는 새 요청/소켓을 닫고 server close와 `shutdownOnce()` 완료를 모두 기다린 뒤에만 종료한다. 테스트 가능한 shutdown coordinator에 exit 동작을 주입하며, cleanup 완료 전 exit 호출은 0회여야 한다.

시작 순서:

1. dataDir 생성.
2. `initializeSqliteStorage({ userDataPath: dataDir })`.
3. `repairStoredOvertimePerformanceData()`.
4. route/session/dialog runtime 생성.
5. `127.0.0.1` listen.
6. listen 뒤 `restartDatabaseBackupRuntime({ userDataPath })`.
7. 원본과 같이 1,200 ms 뒤 file watch, 3,000 ms 뒤 performance recovery를 한 번 예약. 오류는 로그하고 서버를 죽이지 않는다.

종료 순서:

1. 새 요청 차단, 열린 socket 정리.
2. 예약 timer 취소, dialog queued/active child 취소·await.
3. `closeFileWatchRuntime()` await.
4. `stopDatabaseBackupRuntime()`.
5. session map 및 원본 auth state 정리.
6. `closeSqliteStorage()`.

테스트는 lifecycle/dialog/auth 의존성을 주입한다. 실제 dataDir 대신 `mkdtemp`를 쓰고 저장소의 `data/`에 시험 파일을 남기지 않는다. SIGINT/SIGTERM listener는 각각 한 곳에서 한 번만 등록하고 테스트 뒤 제거한다. close를 두 번 불러도 dialog/file-watch/backup/auth/sqlite cleanup은 각각 한 번이어야 하며, cleanup Promise가 끝나기 전 exit 동작은 호출되지 않아야 한다.

### D10. 전체 구현을 3개 슬라이스로 나눈다

| Slice | 범위 | 종료 시 서버 등록 |
|---|---|---:|
| S1 | D1~D9 기반, browser bridge 111, core routes | 17 |
| S2 | operations routes + openFile/openFolder/template save 연결 | 57 |
| S3 | workforce + performance + allowance, openPath, 최종 전수 검증 | 111 |

각 슬라이스는 별도 HANDOFF·검증·커밋이다. 앞 슬라이스가 Sol 검증을 통과하기 전 다음 슬라이스를 시작하지 않는다. 중간 슬라이스에는 누락 endpoint용 성공 stub을 만들지 않는다. 아직 등록되지 않은 채널은 기존 404를 유지한다.
