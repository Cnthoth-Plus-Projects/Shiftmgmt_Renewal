**왜 ① 만으로는 안 되나** — 두 저장소 모두 `.gitattributes` 가 없고 `core.autocrlf=true` 라, git 이 add 때 LF 로 정규화하고 체크아웃 때 CRLF 로 되돌려 쓴다. 그래서 새로 clone 하면 **순수 LF 6개 + 혼재 3개 = 9개**의 작업 파일 바이트가 별첨과 달라진다(§0-가 · 실증 2026-09-10).
🔴 **혼재 3개는 어떤 체크아웃 설정으로도 원본 바이트를 복원할 수 없다** — blob 이 이미 혼재 패턴을 지웠으므로 `autocrlf=true` 면 전부 CRLF, `false`/`input` 이면 전부 LF 가 된다. 따라서 **「작업 트리 SHA-256 == 별첨」을 clone 사본의 합격 조건으로 삼으면 안 된다.**

## 7. 판정 항목 (Codex ⑥ 2차 재제출 검증용)

① **⑥ 1차의 재제출 조건 2건이 닫혔는가** — (가) 「테스트 111파일」 정정(→ 물리 **112** · 1-4 대상 **110**)이 **완료 기준 2 자체에 숫자로** 박혔는가(§1-2 · `TODO.md` 2곳). (나) 정본이 v1.4 로 올라가 **검사기 v0.6 · blob 기준 · 줄바꿈 사실 · 자리 패키지 선언 집합**을 반영했는가.
② **정본 명령이 맞는가** — §1-1 의 명령을 **현재 V4** 와 **새 clone** 두 곳에서 돌려 각각 `matched 122 · eol only 0` / `matched 113 · eol only 9`, 둘 다 `blob match 122 / 122` · `scope changed 129 (allowed 129)` · RC 0 인가.
③ **D-8 의 두 보증 분리가 정확한가** — ①(이관 순간)과 ②(지속·clone)의 경계, 「혼재 3개는 복원 불가」 서술에 사실 오류가 없는가. 줄바꿈 구성 **CRLF 104 · LF 6 · 혼재 3 = 113** 을 직접 세어 확인해 달라(⑥ 1차에서 당신이 센 값과 내 값이 일치했다).
④ **자리 패키지 선언 집합 표(§4 ④)가 `index.d.ts` 실제 내용과 일치하는가** — 그리고 §0-라 의 변이 실측(멤버 **27/27** 실패 · 최상위 9줄은 문법 오류 · 살아남은 선언 0 · 오류가 pdf-service 안에서만)이 재현되는가. **⑥ 1차의 「25건」이 재현되지 않은 것은 내가 스스로 찾아 정정했다.** 이 정정 방식이 충분한가.
⑤ **검사기 v0.6 을 v1.4 와 같은 시각에 🔒 LOCK 해도 되는가** — 당신이 ⑥ 1차에서 이미 AGREE 했고 **코드는 그 뒤 바뀌지 않았다**(`5feb807ec44dd730e6146a676888d1cd96fab758ff31c002872577aa477228d1` 20,308 B · 428줄 — 이 회신 시점에 재실측해 확인해 달라).
⑥ **v1.3 → v1.4 의 차이가 「문서만」인가** — 편집한 자리는 **12곳**이고 `diff -u v1.3 v1.4` 는 **6 hunk · 추가 91줄 · 삭제 18줄**이다(`grep -c "^+"`·`"^-"` 에서 파일 머리 2줄을 뺀 값 · 빈 줄 포함. §8 끝의 목록이 그 12곳이다). 그 밖에 손댄 곳이 있는가. 복사 대상 122개 · 별첨 목록 v0.2 · 생성기 · 검사기 코드는 **SHA 가 그대로**여야 한다.
