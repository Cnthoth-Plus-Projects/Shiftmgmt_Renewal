## 0. 승인된 Task 범위 — 사용자 추가 지시 반영

- 사용자는 전날 약5시간의 필요성에 의문을 제기하고, 예정 작업을 Task로 구조화하여 목록 밖 작업을 막고 불필요 작업을 최소화하도록 지시했다. 그5시간 전부가 필수였다고 가정하지 않는다.
- 현재 실행 큐는 TODO.md다. `.ai/task-plan.json`의 Task ID/다음 Task/계획 hash를 맞춘다. 한 번에 다음 leaf Task 하나만 실행하고, 하위 에이전트도 같은 Task의 근거만 다룬다.
- 구현 전 자체검문/fixture/기존 소스 실측과 구현 후 새 제품 통합/변경 binding/기존 수용 회귀를 구분한다. 없는 코드의 성공을 구현 착수 선행조건으로 요구하지 않는다.
- 필수 결함·검사는 같은 Task/allowlist 안에서 처리한다. 목록 밖 신규 기능·일반 정리·의존성·새 검증 프레임워크는 자동 실행하지 않고, 필요한 최소 변경만 근거와 함께 승인 Task로 추가한다.
- 원래 거절 범위는 기존 검사와 대응시켜 재사용/묶음 실행한다.52개 조건을52개 새 작업으로 키우지 않는다. 독립 빌드는 동일 source/hook/compiler fingerprint에 재사용 가능한 정본 증거를 먼저 검토하고, 각 사용 때 fresh source/정본 bundle/actual served bytes를 검증한다. fingerprint가 바뀌면 재빌드한다. 동등성은 후속 정본에 고정하고 이전 봉인 파일은 수정하지 않는다.
- 준비30분에 재사용/남은 blocker를 정리하고,60분간 구체 패킷 산출물이 없으면 접근을 재검토한다. 시간 때문에 검문을 생략하거나 자동 중단하지 않는다. 매 작은 단계의 진행 허가를 다시 요구하지 않는다.
- 상태는 TODO·HANDOFF·기존 장부/receipt에 필요한 만큼만 기록한다. 새 중복 보고서/메타검문 프로젝트는 기본 산출물이 아니다.

## 2. 실행 순서

| 단계 | 실행할 일 | 다음 단계 조건 |
|---|---|---|
| 착수 | 목표·허용 범위·필수 검문·예상 시간 범위·원래 timeout을 적는다. 예상에 실측이 없으면 추정이라고 표시한다. | 명령 목록과 성공 조건의 모순 없음 |

| 집중 재현 | 실패한 동작을 가장 작은 명령으로 재현하고 원인을 분류한다. | 재현과 수정 근거가 연결됨 |

작은 문서 수정에 제품 전체 시험을 실행하지 않는다. 기존 계약이 요구하는 실제 런타임/UI/음성 시험은 부분 검증이나 문서 검토로 대체하지 않는다.

## 3. 전체 검증 시작 전 Sol 확인

1. **명령 계획**: 순서·고유 이름·argv·기대 RC·필수 시나리오 ID가 명시된 기준과 일치하는지 확인한다. 원 시나리오 수와 pre/post 검사 수를 별도 표기하고 합계를 대조한다. 실행 목록의 길이끼리만 비교하는 검사는 충분하지 않다.
2. **판독 계약**: 기존 샘플/통제 fixture로 최종 상태 문자열·필드·개수·실패 출력 형식이 현재 실행기와 일치하는지 확인한다. 최종 결과를 만드는 코드까지 점검한다.
3. **기존 경로**: 해당 작업이 실행 분기/관측기를 바꾸면 기존 CLI와 무관측 경로도 집중 검문에 포함한다.
4. **대표 실제 실행**: 브라우저/프로세스/파일 판독을 바꾸는 경우, 가장 작은 실제 경로와 최종 독립 판독을 먼저 통과시킨다. 환경 병목이 의심되면 단계별 시간을 먼저 측정한다.
5. **착수 판정**: 위 근거가 없으면 긴 전체 실행을 진단 수단으로 시작하지 않는다. 먼저 준비·집중 재현을 끝낸다.

기존에 봉인된 제어 정본·과거 기록은 수정하지 않는다. 앞으로 작성할 계획은 명시적 시나리오 목록과 집계 기준을 함께 검토하고, 정본 발행 전에 모순을 제거한다.

## 4. 실패와 재실행 기준

- 실패를 `PRODUCT` / `VALIDATOR` / `ENVIRONMENT` / `REPORTING` / `UNKNOWN`으로 분류한다. 원 명령·RC·로그와 가설을 남긴다. 개수 불일치만 보고 제품 결함으로 단정하지 않는다.
- 수정 후에는 먼저 실패 지점과 관련 부분 검문을 실행한다. 전체 재실행에는 **직전 실행과 달라진 소스·제어·환경, 해결 근거, 다시 필요한 검문 범위**를 한 줄로 적는다.
- 같은 소스·제어·환경에서 동일 실패가 **2회** 발생하면 같은 전체 명령을 다시 시작하지 않는다. 최소 재현·단계별 시간 측정·다른 가설로 전환한다. 일시적 환경 오류 재시도도 이 횟수에 포함한다.
- 실패 진단을 시작한 뒤 **20분** 동안 원인이 좁혀지지 않거나, 같은 작업에서 검증기 수정이 **2회** 발생하면 Sol이 계획을 재검토한다. 원래 목적을 다시 확인하고, 변경을 늘리기 전에 기존 흐름에서 해결할 방법을 선택한다. 제어 버전 이름을 바꿔 횟수를 초기화하지 않는다.
- 시간 기준은 **접근 방법을 바꾸고 상황을 보고하는 기준**이다. 승인된 작업을 중단하거나 원래 timeout을 늘리거나 검문을 생략하는 근거로 쓰지 않는다. 오래 걸리는 정상 전체 실행을 20분에 종료하지 않는다.
- 추가 전체 실행은 실제 변경·새 실패·무효화된 증거 등 사유가 있을 때 한다. 마지막 성공 후 변화가 없으면 안심을 위한 중복 전체 실행을 하지 않는다.

## 5. 증거 재사용과 검증기 수정

- 진단용으로 재사용할 때도 해당 결과의 소스·제어·환경·명령·입력·원문 해시가 일치하는지 확인한다. 달라진 의존성이 있으면 관련 결과는 무효다.
- 기존 계약이 신선한 전체 실행을 요구하면 그대로 실행한다. 증거 재사용을 이유로 완료 조건을 바꾸지 않는다.
- 검증기의 집계/판독 결함이면 원 실패를 보존하고 결함의 범위를 먼저 입증한다. 수정 전후 기준·실제 시나리오 목록·추가된 검사·변경된 검증 코드와 독립 검토 근거를 명시한다.
- 기록 재판독은 `RECORDED_EVIDENCE_REVALIDATION`, 새 실행은 `FRESH_EXECUTION`으로 구분한다. 재판독을 원 driver RC0 또는 새 전체 실행 성공으로 보고하지 않는다. 검증기 수정에도 기존 모든 의미 검문과 제품 보호 경계를 유지한다.
- 새 일반 검증 프레임워크·광역 최적화·제어 체계 증설은 이번 결함의 최소 해결에 필요한지 먼저 검토한다. 기존 도구와 집중 명령으로 해결되면 그 방법을 사용한다.

## 6. 시간과 진행 보고

- 시작할 때 단계와 예상 시간 범위를 알린다. 긴 전체 검증은 실측 또는 추정 실행 시간을 시작 전에 따로 알린다.
- 작업 중 **60초 이내 간격**으로 확인한 사실·현재 실행·다음 판단을 짧게 보고한다. 새로운 사실이 없으면 진행 중인 명령과 경과 시간을 알린다. 긴 명령은 짧게 yield/poll하며 실제 프로세스를 유지한다.
- 예상 상한을 넘으면 원인·확인된 범위·다음 조치를 즉시 알리고 자율적으로 진행한다. 필수 승인 없이 계속할 수 있는 일에 확인 질문을 추가하지 않는다.
- “완료/통과”는 최종 결과 파일과 실제 종료 상태를 읽은 뒤에만 말한다. 하위 명령 수, 마지막으로 보인 PASS, 계획 검사는 전체 완료 근거가 아니다. 전체 RC1이면 실제로 통과한 범위와 미해결 판정을 함께 적는다.
