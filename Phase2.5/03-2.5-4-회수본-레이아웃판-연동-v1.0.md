## 1. 목표와 완료 조건

배포한 근무표 XLSX가 기본 위치이든 사용자가 저장한 조정 위치이든, 회수 시 **배포 당시 레이아웃 판**을 찾아 같은 실적으로 해석한다. 다음을 모두 만족해야 완료다.

1. template1·template2 기본 레이아웃의 배포→회수→해석 결과가 기존과 같다.
2. 판독 블록 위치를 조정해 저장한 template1·template2도 배포→회수→해석 결과가 기본 레이아웃과 같다.
3. 배포 후 더 새 레이아웃을 활성화해도 과거 배포 파일은 파일에 기록된 당시 판으로 읽는다.
4. 알 수 없는 판, 판/변형 불일치, 메타데이터 손상, 보호 구조 변조는 현재 활성 판으로 추측하지 않고 저장 전에 실패한다.
5. Phase 2.5-4 이전의 정상 근무표는 메타데이터가 없어도 **정확한 구형 기본 구조**일 때만 계속 읽는다.

## 3. 판 식별 메타데이터 계약

### 3.1 저장 위치

- 워크시트 이름: `__shiftmgmt_meta`
- 상태: ExcelJS `veryHidden`
- 값 위치: `A1` 단일 셀
- 정의 이름: `_SHIFT_MGMT_SCHEDULE_LAYOUT_REVISION`
- 정의 이름은 정확히 `__shiftmgmt_meta!$A$1` 한 범위만 가리킨다.
- 메타데이터 시트에는 `A1` 외 업무 데이터나 판독 원본을 복제하지 않는다.

이 위치는 사용자에게 보이는 `교대 근무 계획표`의 어떤 업무 셀도 덮어쓰지 않는다. 숨김은 보안 경계가 아니라 사용자 셀과의 충돌을 피하는 저장 규약이다.

### 3.2 JSON v1

`A1`은 아래 필드만 가진 JSON 객체다. 객체 키를 사전순으로 정렬한 단일행 canonical JSON을 기록한다.

```json
{
  "definitionSha256": "<64 lowercase hex>",
  "format": "shiftmgmt.schedule-layout-revision",
  "generatorCompatibilityVersion": "built-in-excel-layout-v1",
  "layoutKey": "schedule-xlsx/template1",
  "revisionId": "<stored UUID 또는 builtin:layoutKey:definitionSha256>",
  "revisionKind": "stored",
  "schemaVersion": 1
}
```

- `layoutKey`: `schedule-xlsx/template1` 또는 `schedule-xlsx/template2`
- `revisionKind`: `stored` 또는 `built-in`
- 저장 판의 `revisionId`: `document_template_versions.id`의 기존 불변 UUID
- 내장 판의 `revisionId`: `builtin:<layoutKey>:<definitionSha256>` 형식의 결정적 합성 ID
- `generatorCompatibilityVersion`: 정의가 이미 가진 `generatorCompatibilityVersion`과 동일
- `definitionSha256`: §3.3의 정의 digest
- 추가 필드, 누락 필드, 잘못된 타입, 중복/충돌 정의 이름, 보이는 메타 시트, 다른 셀/범위를 가리키는 정의 이름은 오류다.

### 3.3 정의 digest

전체 `DocumentLayoutDefinition`을 다음 규칙으로 canonical JSON화한 뒤 Node 내장 `crypto`의 SHA-256을 계산한다.

- 객체 키는 모든 깊이에서 사전순 정렬한다.
- 배열 순서는 보존한다.
- JSON이 지원하지 않는 값은 허용하지 않는다.
- 출력은 공백 없는 JSON 문자열이다.
- 외부 패키지를 추가하지 않는다.

digest는 우발적 불일치와 잘못된 판 선택을 탐지한다. 비밀키가 없는 해시이므로 악의적 위조를 막는 서명으로 주장하지 않는다.

## 4. 판 해석 규칙

### 4.1 저장 판

내부 서비스에 `(layoutKey, revisionId)`로 `source_path = ''`인 정확한 행 하나를 조회하는 함수를 추가한다. 활성 여부와 무관하게 `profile_json`을 파싱하고, 문서 종류·variant·스키마·generator 호환성을 기존 정의 검증기로 다시 검증한다.

- 없는 ID, 다른 layoutKey 소속 ID, 중복 행, 빈/잘못된 JSON, 유효하지 않은 정의는 오류다.
- 현재 활성 판으로 대체하지 않는다.
- 외부 API나 history 응답은 확장하지 않는다.

### 4.2 내장 판

내장 판은 현재 번들에 포함된 해당 `layoutKey`의 정의를 canonical digest로 계산해 metadata의 ID·digest와 모두 대조한다. 일치하지 않으면 오류다.

내장 정의가 장래에 바뀌면 과거 판을 호환 registry로 명시적으로 보존해야 한다. registry가 없는 과거 내장 ID를 현재 정의로 추측하지 않는다.

### 4.3 메타데이터가 있는 파일

1. 메타 시트·정의 이름·JSON 스키마를 엄격히 확인한다.
2. `revisionKind`에 따라 정확한 저장 판 또는 알려진 내장 판을 찾는다.
3. `layoutKey`, `revisionId`, `generatorCompatibilityVersion`, `definitionSha256`를 모두 대조한다.
4. 그 역사적 정의로 좌표를 계산하고 보호 구조를 확인한 뒤에만 업무 값을 읽는다.
5. 어느 단계든 실패하면 오류를 반환하고 실적 저장 건수는 0이어야 한다.

### 4.4 메타데이터가 없는 구형 파일

메타데이터가 전혀 없을 때만 legacy 경로를 허용한다. template1/template2 각각의 Phase 2.5-4 이전 기본 보호 구조와 정확히 맞아야 한다.

- 정상 구형 기본 샘플: 허용
- 메타데이터 일부만 존재: 오류
- 메타데이터를 제거한 조정 레이아웃: 오류
- 구조가 이동·변조됐는데 옛 고정 셀 일부만 우연히 남은 파일: 오류

Phase 2.5-4 전에는 판독 블록 위치의 운영 저장이 차단됐으므로, 유효한 “구형 조정 배포본”은 존재하지 않는다는 사실을 호환 경계로 쓴다.

## 5. 정의 기반 좌표 도출

`computeDocumentLayoutActualBlockRanges(definition)`의 schedule `targetRanges`를 재사용한다. 고정 주소를 새 사본으로 만들지 않는다.

- 각 역할 셀은 내장 기본 정의의 블록 시작점에 대한 기존 셀의 상대 offset으로 표현한다.
- 같은 offset을 역사적 정의의 target range 시작점에 적용한다.
- 이동 가능한 판독 블록은 `calendar-grid`, `reschedule`, `substitute`, `overtime` 네 개다.
- renderer 이동의 영향을 받는 `site`, `calendar-heading`, `roster`의 실제 업무 셀도 같은 방식으로 번역한다.
- `schedule.month-anchors`는 보호된 기존 위치를 유지한다.

현재 의미를 보존해야 하는 대표 offset은 다음과 같다.

| 역할 | 기본 의미 | 번역 규칙 |
|---|---|---|
| 사업장 | `C3` | `schedule.site` 내부 offset |
| 월 제목 | `W6` | `schedule.calendar-heading` 내부 offset |
| 근무자 요약 | `B7` | `schedule.roster` 내부 offset |
| 달력 DATE/주차·근무 칸 | 현행 `DATE` 행과 variant별 열 | `schedule.calendar-grid` 내부 offset 집합 |
| 근무 변경 일자·근무·사유 | 현행 `Y12...`와 variant별 열 | `schedule.reschedule` 내부 offset 집합 |
| 대체근무 | 현행 11~26행, 16행 | `schedule.substitute` 내부 offset, 16행 유지 |
| 연장근무 | 현행 34~100행, 67행 | `schedule.overtime` 데이터 시작 offset과 67행 window 유지 |

특히 overtime 블록의 스타일 높이 11행만 스캔하도록 줄이지 않는다. 현재 지원 용량인 67행을 블록 이동량만큼 평행 이동한다. 조용한 데이터 절단은 실패다.

## 6. 보호 구조 검증

역사적 정의로 내장 원본에 renderer를 적용한 참조 구조를 만들고, 회수 워크북의 parser-critical 구조와 비교한다. 사용자가 입력하는 값과 편집 허용 속성은 비교 대상이 아니다.

최소 검증 대상:

- 판독 블록의 대상 범위와 경계
- variant를 구분하는 변경 사유 머리글과 각 표의 정적 머리글
- `DATE` 표식과 달력/변경/대체/연장 표의 parser anchor
- parser-critical 범위와 교차하는 병합의 정확한 집합
- 보호된 행 높이
- 정의의 문서 종류·variant·binding/블록 identity

열 너비와 글꼴은 현행 편집 허용 속성이므로 구조 변조로 판정하지 않는다. 업무 입력 셀의 값·채우기 역시 정상 회수 편집으로 허용한다.

## 7. 저장 활성화 전환

`document-layout-definition-service.ts`의 `SCHEDULE_PARSER_POSITION_NOT_ACTIVATABLE` save-mode 오류만 제거한다. 기존 capability, 충돌 검사, 범위 검사, 크기·visibility·text·binding·row-height·merge 보호는 그대로 둔다.

이 전환은 §3~§6의 메타데이터·역사 판 조회·정의 기반 좌표·구조 검증이 함께 구현되고 시험을 통과할 때만 유효하다. 일부만 구현한 상태에서 위치 저장만 열면 안 된다.

## 8. 오류와 인테이크 원자성

- 메타데이터/판/구조 오류는 기존 파일 인테이크 오류 경로로 전달한다.
- 실패한 파일에서 실적 행을 일부라도 저장하지 않는다.
- 오류 때문에 현재 활성 정의 또는 기본 좌표로 fallback하지 않는다.
- 오류 메시지는 적어도 `metadata`, `revision`, `layout key/variant`, `protected structure` 중 실패 종류를 식별할 수 있어야 한다.

## 9. 보존할 제품 불변조건

- 실적 입력 경로는 Excel 인테이크뿐이다. 시험도 DB에 직접 실적을 삽입하지 않는다.
- 결과 정렬은 기존 team → sortOrder → employee code 의미를 바꾸지 않는다.
- Pool/BP/사번 없음 제외·경고 규칙을 유지한다.
- 대체근무 수당, 휴일, 연장·야간·휴게 계산을 변경하지 않는다.
- 고정행 제거는 위치 계산만 바꾸는 것이며 현재 행 용량이나 판정 규칙을 줄이지 않는다.
- V3.4는 읽기 전용이다.
