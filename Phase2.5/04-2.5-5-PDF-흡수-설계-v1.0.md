## 1. 결론

Phase 2.5-5는 다음 다섯 결과를 한 묶음으로 구현해야 완료다.

1. `proposal-pdf`와 `dashboard-report-pdf`를 내장 기본 레이아웃, 저장·조회·초기화·이력·미리보기의 정식 지원 키로 연다. 기존 Excel 5키와 합쳐 지원 키는 7개다.
2. 품의서·별첨1·별첨2 PDF와 대시보드 PDF를 `scripts/lib/find-chrome.mjs`가 찾은 **설치된 Chrome**으로 만든다. 실행 중 브라우저 다운로드, 인터넷, AI, 외부 API, Electron은 사용하지 않는다.
3. PDF 생성기는 저장된 레이아웃 정의의 위치·크기·표시·정적 문구·로고·열 폭·글꼴 변경을 실제 HTML/CSS에 반영하고, 값·바인딩·행 순서·행 높이·병합·쪽/흐름 구조는 계속 보호한다.
4. V4에서 의도적으로 막아 둔 대시보드 내보내기 호출점을 복구한다. 기존 공개 계약대로 XLSX와 PDF가 모두 동작하며, 성공했을 때만 `dashboard-export` 활동을 기록한다.
5. Electron import와 `vendor/electron-compat`를 완전히 제거하고 `playwright`를 런타임 의존성으로 옮긴다. 사용자 오류에는 Electron·Playwright·실행 파일 경로·스택을 노출하지 않는다.

단순히 `printToPDF`를 다른 호출로 바꾸는 것은 완료가 아니다. PDF 키가 계속 비노출이거나, 대시보드 라우트가 계속 실패하거나, 레이아웃 변경이 실제 PDF에 반영되지 않으면 Phase 2.5-5는 미완료다.

## 3. 런타임 PDF 엔진

### 3.1 공용 서비스

새 `installed-chrome-pdf-service.ts`는 다음 두 층을 제공한다.

- `renderHtmlToPdfBytes`: HTML을 받아 검증된 PDF `Buffer`를 반환한다.
- `commitPdfBytesAtomically`: 완성된 bytes를 대상과 같은 디렉터리의 임시 파일에 배타적으로 쓴 뒤 완성본만 대상 이름으로 노출한다.

서비스는 `scripts/lib/find-chrome.mjs`의 `findChrome()`를 사용한다. Chrome 검색 규칙을 TS 서비스에 복사하지 않는다. 서버 빌드가 CommonJS이고 finder가 ESM `.mjs`이므로 `pathToFileURL()` + 런타임 native `import()`를 사용하며, `require()`로 `.mjs`를 읽지 않는다. finder 모듈 후보는 다음 두 위치만 허용한다.

1. `<project-root>/scripts/lib/find-chrome.mjs` — `__dirname`에서 루트까지 계산
2. `<process.cwd()>/scripts/lib/find-chrome.mjs`

둘 다 일반 파일이 아니거나 import/export 모양이 다르면 한국어 안전 오류로 중단한다. Chrome 실행 파일을 별도 규칙으로 다시 찾는 fallback은 금지한다.

### 3.2 Playwright 호출 계약

- `chromium.launch({ executablePath: found.path, headless: true })`
- 새 browser context와 page를 요청마다 만들고 항상 닫는다.
- HTML은 `page.setContent(html, { waitUntil: "load" })`로 넣는다.
- `document.fonts.ready`를 기다린다.
- `page.pdf({ printBackground: true, preferCSSPageSize: true, displayHeaderFooter: false })`
- 전체 제한 시간 기본 30,000ms. timeout, page, context, browser cleanup을 `finally`에서 보장한다.
- 모든 `http:`·`https:`·`file:`·기타 외부 요청을 abort한다. 문서 자체와 검증된 `data:image/png|jpeg;base64,...`만 허용한다.
- 반환 bytes가 비어 있거나 첫 5바이트가 `%PDF-`가 아니면 실패한다.
- 브라우저 다운로드나 Playwright bundled browser fallback은 금지한다.

### 3.3 원자적 저장과 3파일 묶음

- 임시 파일은 대상과 같은 디렉터리에 UUID 기반 숨김 이름으로 만들고 `wx`로 연다.
- 완성 bytes를 쓴 뒤 같은 볼륨의 hard-link 또는 동등한 배타적 commit으로 대상 이름을 만든다. 기존 대상은 덮어쓰지 않는다.
- 성공·실패 모두 임시 파일을 지운다.
- `proposal-pdf`는 세 HTML을 **전부 PDF bytes로 성공 렌더링한 뒤** 세 대상을 commit한다.
- commit 중 실패하면 이번 호출이 새로 만든 대상만 역순으로 제거한다. 호출 전 존재하던 파일은 절대 삭제·덮어쓰기 하지 않는다.
- DB export 기록은 세 파일 commit이 모두 끝난 뒤에만 저장한다.

### 3.4 사용자 오류

사용자에게 허용되는 대표 문구는 다음 의미를 유지한다.

- Chrome 없음/실행 불가: `PDF를 만들 수 없습니다. 이 컴퓨터의 크롬 설치 상태를 확인해 주세요.`
- 제한 시간: `PDF 생성 시간이 초과되었습니다. 잠시 후 다시 시도해 주세요.`
- 잘못된 이미지: `차트 이미지 형식이 올바르지 않습니다. PNG 또는 JPEG 이미지를 사용해 주세요.`
- 일반 실패: 해당 기능의 기존 한국어 실패 코드와 한국어 설명

`Electron`, `Playwright`, stack, `chrome.exe` 절대 경로, finder가 탐색한 경로 목록은 사용자 응답에 넣지 않는다.

### 4.1 상수와 지원 집합

- `PDF_LAYOUT_GENERATOR_COMPATIBILITY_VERSION = "built-in-pdf-layout-v1"` 추가
- `SUPPORTED_DOCUMENT_LAYOUT_STORAGE_KEYS`를 다음 순서로 추가
  1. `schedule-xlsx/template1`
  2. `schedule-xlsx/template2`
  3. `proposal-xlsx`
  4. `attachment1-xlsx`
  5. `attachment2-xlsx`
  6. `proposal-pdf`
  7. `dashboard-report-pdf`
- `SUPPORTED_EXCEL_LAYOUT_STORAGE_KEYS`는 Excel 생성기 전용으로 유지한다.
- 저장·조회·이력·초기화·미리보기 지원 gate는 7키 집합을 쓴다.

공개 bridge 계약은 이미 두 PDF `DocumentKind`, `application/pdf`, 다중 `outputs`를 포함한다. 새 채널이나 공개 타입을 만들지 않는다.

### 4.2 검증기 일반화

검증기는 `outputs[0]` 단일 처리를 없애고 모든 `outputs[i]`를 기본 정의의 같은 인덱스와 대조한다.

- 멤버 수, 순서, `memberId`, canvas, filename pattern, block 수·순서·ID를 전 멤버에서 검증한다.
- issue path는 실제 인덱스인 `outputs[1]...`, `outputs[2]...`를 보고한다.
- 블록 ID는 definition 전체에서 유일해야 한다.
- capability는 output 순서와 block 순서대로 모든 블록을 평탄화한다.
- compatibility version은 document kind의 기본 정의 값과 정확히 같아야 한다.
- `unit="cell"` 좌표·크기는 현행처럼 양의 정수 규칙을 유지한다.
- `unit="mm"` 좌표·크기는 유한한 0 이상/양수 실수를 허용한다.
- canvas 자체와 `page`, `layoutMode`, `flowOrder`, `autoHeight`, `repeatHeaderOnPageBreak`, `pageBreakBefore`는 보호한다.
- PDF flow 블록은 자동 흐름이라 직사각형 충돌 검사를 적용하지 않는다. 같은 page의 absolute 블록과 Excel 블록에는 기존 충돌 규칙을 적용한다.
- `logoAssetId` 속성이 있는 블록은 kind가 `logo`가 아니어도 기존 capability에 `logo` 편집을 추가한다. title 안 로고를 지원하기 위한 규칙이다.

### 4.3 파일명 패턴

정규 token 집합과 확장자는 다음과 같다.

| kind | 허용 token | 확장자 |
|---|---|---|
| `schedule-xlsx` | `year`, `monthNumber`, `month2`, `siteName` | `.xlsx` |
| 수당 Excel/PDF | `year`, `month2` | 해당 kind의 `.xlsx`/`.pdf` |
| `dashboard-report-pdf` | `name`, `timestamp` | `.pdf` |

Phase 2.5-1 §10의 `{month}`는 같은 문서 §12와 기존 도메인 token에 맞춰 **두 자리 월 `{month2}`**로 정규화한다. 내장 수당 PDF pattern은 연/월 폴더까지 포함한다.

대시보드의 한 정의가 단일 차트와 보고서를 함께 지원하므로 내장 pattern은 `{name}_{timestamp}.pdf`다.

- 차트의 보호 파생 `name`: `${chartKey}_${chartTitle}`
- 보고서의 보호 파생 `name`: `title`
- `timestamp`: ISO 시각의 `YYYY-MM-DD-hh-mm-ss`

token 값은 Windows 금지 문자·제어문자·경로 구분자를 `_` 또는 기존 정규 치환 문자로 바꾼다. 미치환 token, 절대경로, `..`, 역슬래시, 확장자 불일치는 저장·미리보기 모두 거절한다. 같은 경로가 있으면 `_dup01`, `_dup02`를 붙이고 덮어쓰지 않는다.

## 6. 레이아웃을 HTML/CSS에 적용하는 규칙

생성기는 현행 HTML과 계산 로직을 기본 출력 정본으로 유지하고, active definition과 built-in definition의 **delta**만 적용한다.

1. 각 wrapper에 `data-layout-block-id="..."`를 붙인다.
2. `visible=false`이면 해당 wrapper를 출력하지 않는다.
3. flow 순서는 baseline `flowOrder`대로 고정한다.
4. `x` 차이는 baseline 대비 `margin-left` mm, `y` 차이는 baseline 대비 `margin-top` mm로 반영한다. DOM 순서를 바꾸지 않는다.
5. width 변경은 wrapper width/max-width mm, height 변경은 min-height mm로 반영한다. 동적 데이터가 잘리지 않도록 고정 `height`나 overflow hidden을 쓰지 않는다.
6. 정적 `text`만 지정된 inner text node를 교체한다. `bindingKey`가 있는 값, 표 머리글·행·합계·차트 값은 바꾸지 않는다.
7. `logoAssetId="brand-logo"`면 공용 logo buffer의 data URL을 쓰고, `null`이면 로고만 숨긴다.
8. table `columnWidths`는 양수 가중치를 100%로 정규화해 `<colgroup>`에 적용한다.
9. font delta는 `family`, `sizePt`, `bold`, `italic`, `color`를 CSS로 옮긴다. `sizePt`는 `pt` 단위를 유지한다.
10. 기본 definition이면 현재 HTML/CSS 결과가 달라지지 않아야 한다.

품의서 압축 점수 11/15, 차트 정렬·합계·최대 8줄, donut 계산, 별첨 정렬·소계·합계, 요율 안내 1/2/3열 임계값, dashboard section page break, 반복 thead, 빈 데이터 문구는 보호한다.

## 7. 로고와 데이터 안전

### 7.1 로고

`document-brand-logo-service.ts`의 기존 파일 탐색을 하나의 public resolver로 승격한다.

- `resolveBrandLogoBuffer(): Buffer | null`
- `resolveBrandLogoDataUrl(): string | null`

Excel과 PDF가 같은 bytes를 사용한다. `nativeImage` 기반 배경 정규화는 제거한다. 정본 `brand-logo-clean*.png` 자체를 data URL로 넣는다. 테스트 resolver 주입 계약은 유지한다.

### 7.2 대시보드 이미지

`chartImageDataUrl`은 출력 형식과 무관하게 파일 생성 전에 전 section을 검증한다.

- 허용: `data:image/png;base64,...`, `data:image/jpeg;base64,...`
- 공백·줄바꿈·추가 parameter·SVG·HTML·URL·file path 거절
- base64 문법과 canonical round-trip 확인
- PNG signature 또는 JPEG SOI/EOI 확인
- decoded 최대 10 MiB
- 하나라도 잘못되면 파일을 만들지 않는다.

모든 title, filter, column header, row value, alt attribute는 HTML escape한다. 동적 문자열을 `<style>`이나 script에 삽입하지 않는다.

## 8. 서비스 연결

### 8.1 수당 PDF

`allowance-document-export-service.ts`의 PDF 분기는 다음 순서다.

1. `getDocumentLayout({ documentKind: "proposal-pdf" })`
2. `outputs`가 proposal/attachment1/attachment2 순서인지 검증
3. 각 member pattern을 공용 resolver로 실제 target path로 변환
4. active definition 전체와 세 target을 `writeAllowancePdfDocuments`에 전달
5. writer가 HTML delta 적용 → 세 PDF bytes 렌더 → 원자적 batch commit
6. 전부 성공 후 export record 저장

고정 `resolveAllowanceDocumentOutputTarget`의 PDF 사용은 제거한다. XLSX 경로와 계산·대상자 필터는 바꾸지 않는다.

### 8.2 대시보드

V3.4 서비스에서 XLSX writer와 네 개의 기존 service test를 복구하되 Electron PDF 부분은 가져오지 않는다.

- chart: columns 0개 거절. rows 0개는 XLSX/PDF 모두 허용하고 빈 문구를 출력한다.
- report: sections 0개 거절. 각 section rows 0개는 허용한다.
- XLSX: 기존 sheet, metadata, table, totals, image 계약 유지
- PDF: active `dashboard-report-pdf` definition + 공용 Chrome renderer 사용
- output path가 직접 주어져도 확장자를 보정하고 기존 파일은 `_dupNN`으로 피한다.

`core-routes.ts`는 기존 dialog UX를 유지하면서 service를 호출한다. 취소, service failure는 활동 0건이다. 성공한 chart/report만 `dashboard-export` 활동 1건을 기록한다. 공개 contract, channel count, 권한 guard는 변경하지 않는다.

### 8.3 미리보기

`generateDocumentLayoutPreview`는 같은 production writer를 사용한다.

- Excel 5키: 현행 1 artifact 유지
- `proposal-pdf`: proposal → attachment1 → attachment2 순서의 `application/pdf` 3 artifacts
- `dashboard-report-pdf`: synthetic 2-section 보고서 1 artifact. page break와 빈/비빈 표를 함께 포함
- preview URL, UUID, 10분 TTL, temp-root containment, symlink 거절, cleanup 계약 유지
- 가짜 PDF bytes나 테스트 전용 렌더러는 금지

## 9. 의존성과 Electron 제거

- `playwright`를 devDependencies에서 dependencies로 이동한다. 판은 기존 lock 범위 `^1.58`을 유지한다.
- `electron: file:./vendor/electron-compat`를 package와 lock에서 제거한다.
- `vendor/electron-compat/index.d.ts`, `index.js`, `package.json`을 삭제한다.
- 제품 소스·빌드 결과에서 `from "electron"`, `import("electron")`, `nativeImage`, `BrowserWindow`, `printToPDF`가 0건이어야 한다.

- 서비스 두 개 추가로 smoke strict count는 78→80이다.
- codebase map의 runtime dependency, finder 사용처, smoke count, vendor 설명을 실제 상태로 갱신한다.
