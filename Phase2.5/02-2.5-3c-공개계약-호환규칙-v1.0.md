## 1. 목적과 적용 우선순위

Phase 2.5-3c는 파일 등록 기반 양식 공개 채널 10개를 레이아웃 공개 채널 6개로 교체하고, 브리지·HTTP route·관리자 권한·계약 수 시험을 같은 변경에서 동기화한다.

이 문서는 최종 목표 계약을 바꾸지 않는다. 아직 구현되지 않은 PDF와 JSON 단일화가 남은 동안 3c가 거짓 placeholder나 선행 구현을 노출하지 않도록 **과도기 실행 규칙**만 닫는다. 충돌 시 실제 source/runtime/test가 오래된 요약보다 우선하고, 제품 방향은 `04-api-contract.md`와 `TODO.md`가 우선한다.

## 2. 확정 결정

### D3C-01 — 3c 채널 범위

이번 단계에서는 문서 양식 채널 10개만 폐기하고 레이아웃 채널 6개만 추가한다.

- `operations:select-migration-file`은 그대로 둔다.
- `operations:select-json-backup-file` 교체는 Phase 2.5-6이 소유한다.
- 따라서 이번 단계에서 바로 `111 - 10 + 6 = 107`, operations `40 - 10 + 6 = 36`이 된다.
- 2.5-6의 migration selector 교체는 1대1이므로 최종 107/36을 바꾸지 않는다.

### D3C-02 — PDF 비노출

`DocumentKind` 타입에는 최종 목표인 `proposal-pdf`, `dashboard-report-pdf`가 남아 있지만, 3c runtime은 구현된 Excel 저장 키 5개만 공개한다.

- 목록 결과: `schedule-xlsx/template1`, `schedule-xlsx/template2`, `proposal-xlsx`, `attachment1-xlsx`, `attachment2-xlsx`만 반환한다.
- PDF 키를 get/save/reset/preview/history에 직접 넘기면 해당 route의 `DOCUMENT_LAYOUT_*_FAILED`로 실패한다.
- PDF용 기본 정의, 빈 snapshot, 가짜 preview URL, `not implemented` placeholder를 반환하지 않는다.
- PDF 실제 정의·저장·렌더링을 완성하는 Phase 2.5-5에서 같은 6채널의 지원 범위를 넓힌다.

### D3C-04 — 오류 코드

| 채널 | 실패 코드 |
|---|---|
| list | `DOCUMENT_LAYOUT_LIST_FAILED` |
| get | `DOCUMENT_LAYOUT_GET_FAILED` |
| save | `DOCUMENT_LAYOUT_SAVE_FAILED` |
| reset | `DOCUMENT_LAYOUT_RESET_FAILED` |
| preview | `DOCUMENT_LAYOUT_PREVIEW_FAILED` |
| history | `DOCUMENT_LAYOUT_HISTORY_LIST_FAILED` |

서비스가 이미 만드는 한국어 원인 메시지를 보존한다. 인증 전 실패는 기존 서버 가드를 그대로 사용해 세션 없음 `401 AUTH_SESSION_REQUIRED`, 비관리자 `200 AUTH_FORBIDDEN`이며 서비스·파일·활동 기록은 0이다.

### D3C-05 — revision 규칙

- save/reset의 `expectedRevisionId`는 현재 활성 판과 정확히 같아야 한다. 기존 storage service의 transaction·history 동작을 그대로 재사용한다.
- preview의 `basedOnRevisionId`도 생성 시작 시 현재 활성 판과 정확히 같아야 한다. 다르면 preview 파일을 하나도 만들지 않고 실패한다.
- 목록/get/history는 `source_path=''`인 레이아웃 행만 사용한다. 옛 file-template 행은 읽거나 바꾸지 않는다.

### D3C-06 — 만료형 미리보기 URL

미리보기 공개 계약은 filesystem path가 아니라 아래 상대 URL을 반환한다.

```text
/api/document-layout-previews/<previewId>/<memberId>
```

- `previewId`: `crypto.randomUUID()`로 만든 난수 ID.
- 저장 위치: OS 임시 폴더 아래 전용 root. repository·dataDir·DB에는 저장하지 않는다.
- 만료 시간: 생성 성공 시각부터 **10분**.
- `expiresAt`: 같은 만료 시각의 ISO 문자열.
- 생성기는 기존 `generateDocumentLayoutPreview`만 사용한다. 별도 가짜 렌더러나 business DB 데이터를 쓰지 않는다.
- manifest는 서버가 생성한 `previewId`, 만료 시각, memberId, media type, 안전한 상대 파일명만 기록한다.
- GET은 정확한 prefix·UUID·memberId·manifest를 검증하고, 관리자 세션이 있을 때만 artifact bytes를 `Cache-Control: no-store`로 돌려준다.
- 세션 없음은 401, 비관리자는 200 `AUTH_FORBIDDEN`, 잘못된 ID/member/path·누락·만료는 404다.
- 만료 뒤에는 물리 파일 삭제 성공 여부와 무관하게 먼저 접근을 거부한다. 생성/읽기 입력에서 임의 파일 경로를 받지 않는다.
- 생성 실패 시 부분 디렉터리를 정리하고 원래 오류를 반환한다. 정리 실패를 성공으로 바꾸지 않는다.

## 5. 시험 계약

기준선은 2026-09-21 Sol 실측으로 관련 6 files / 61 tests, 전체 128 files / 821 tests, smoke 77이다.

신규 artifact service test에는 정확히 6개를 둔다.

1. 정상 생성 — 난수 ID, 상대 URL, 10분 만료, manifest, generator 호출.
2. stale `basedOnRevisionId` — generator·파일 생성 0.
3. PDF key — placeholder·generator·파일 생성 0.
4. 유효 GET resolve — bytes/media type/file name 일치.
5. 만료 artifact — 접근 거부 후 정리 시도.
6. 잘못된 UUID/member/path traversal/manifest — 전부 파일 노출 0.

`server.test.ts`에는 정확히 1개를 추가해 preview GET의 세션 없음, 비관리자, 관리자 정상 binary, 만료/누락 404를 한 시나리오에서 검증한다. 이 시험은 기존 문자열 응답 helper로 binary를 UTF-8 변환하지 않고 `Buffer`를 그대로 보존해 원본 bytes와 일치함을 단언하며, 정상 응답의 `Content-Type`과 `Cache-Control: no-store`도 직접 단언한다. 기존 네 계약/route test의 `it` 수는 늘리지 않고 111→107, 40→36과 새 매핑·음성 경로로 교체한다.

예상 최종값:

- 집중 7 files / **68 tests**.
- 전체 129 files / **828 tests**.
- smoke service **78**.
- generator 5/5 byte-identical.
- typecheck, lint 0 error(기존 warning 7 이하), build, diff check 통과.
- 초기 28경로 + 허용 기존 9파일 수정 + 신규 2파일 = 최종 최대 39경로. 정확한 status는 이 닫힌 합집합 밖이 0이어야 한다.
