## 6. Sol 코드 전략·오류 처리

1. 착수 게이트: §3의 repo/branch/HEAD/status SHA, 허용 6파일 SHA, 보호 6파일 SHA, 운영 JSON SHA를 실측한다. 모두 일치할 때만 수정한다.
2. C01: live DB의 6운영 키 상태를 close 전에 읽어 값과 ‘키 없음’을 구분해 설정 변환 입력에 전달한다. source 업무 6키는 검증된 JSON에서만 사용한다. 정책 시작일 비교 후 marker의 보존/갱신을 분기하고, 미리보기와 실행이 **동일 변환 함수**를 사용해 실제 행 수·값·`updated_at`을 산출한다. 이미 있던 로컬 marker를 날짜 동일하다는 이유로 없애지 않는다.
3. C02: 파싱 바이트 SHA와 JSON 파싱을 동일 버퍼에서 수행한다. 원본 이름 집합을 런타임 40표 집합과 대조하고, 각 행의 키·값 타입을 표별 스키마/지원되는 V3 차이에 맞춰 전체 행마다 검사한다. 현재 JSON schemaVersion 1의 알려진 호환 차이를 명시적으로 다루되 미지원 비어 있지 않은 표/열을 경고만 내고 버리지 않는다. `insertTableRows`가 첫 행의 열 목록 때문에 뒤 행 값을 묵살하지 않도록 한다. `check`의 ready/details는 실제 검사 범위만 정직하게 알린다.
4. C03: 지문 직렬화는 표·열·행·타입·값 길이의 모호성을 없애고, SQL 결과 순서가 달라져도 동등 DB가 같은 지문이 되게 한다. backup await가 끝난 직후 현재 DB와 원본 파일을 재확인하며, **실제 import에 사용한 파싱 바이트의 SHA도 토큰 SHA와 대조**한다. 그 이후 교체 전 변경도 가능하면 기존 교체 잠금/트랜잭션 경계로 차단한다. 필요한 잠금/트랜잭션을 보호 파일 수정 없이 보장할 수 없으면 조용히 진행하지 말고 `BLOCKED`.
5. C04: 동시 호출이 같은 최종 경로를 고르지 않도록 고유 식별자 또는 배타 예약을 사용하고, 최종 파일 공개에서 기존 파일을 덮어쓸 가능성을 없앤다. 실제 파일을 다시 읽어 SHA를 계산하고, 실패 시 본 호출의 미완성물만 정리한다. 두 호출이 같은 초여도 둘 다 독립 백업이다.
6. C05: `dist` 부모 링크까지 검사한 뒤, `dist/server`가 저장소 밖을 가리키지 않음을 증명하고 청소한다. 격리된 fixture로 링크 거부를 검증하되 실제 외부 경로를 삭제하는 시험을 만들지 않는다.
