### 2. 원칙의 부작용

#### 원칙 1 — 빈 값·0에 이유 표시

- 정상적인 0까지 모두 긴 문장으로 설명하면 표가 사유 문구로 뒤덮인다.
- 업무상 이상하거나 조치 가능한 0만 한 줄 사유 칩으로 강조하고, 정상적인 0은 상세·도움말에서 설명해야 한다.
- 화면이 이유를 추정해서 만들면 안 된다. 서비스가 반환하거나 코드로 확정 가능한 사유만 표시해야 한다.

#### 원칙 2 — 확인창 3종 통일

- 되돌릴 수 있는 동작까지 전부 확인하면 확인 피로가 생겨 사용자가 내용을 읽지 않고 승인한다.
- 단순 확인은 상태 손실 가능성이 있는 경우로 제한해야 한다.
- 승인과 삭제를 모두 빨간 버튼으로 만들면 위험 신호가 무뎌진다. 빨강은 삭제·DB 교체처럼 파괴적인 동작에 집중하고, 승인·품의는 강한 강조와 정확한 결과 설명을 우선한다.
- 실행이 시작된 뒤에는 Esc로 닫거나 재실행할 수 없게 해야 한다.

#### 원칙 3 — 권한 없는 버튼 표시

- 네이티브 `disabled` 버튼은 보통 키보드 포커스를 받지 못하므로 마우스 hover 툴팁만으로 이유를 설명하면 키보드·스크린리더 사용자는 이유를 알 수 없다.
- 포커스 가능한 `aria-disabled` 패턴 또는 버튼 옆의 항상 보이는 설명을 사용해야 한다.
- 현재 역할이 접근할 수 없는 관리자 전용 화면까지 전부 노출할 필요는 없다. 접근 가능한 화면 안의 작업 권한에 적용하는 원칙으로 범위를 정해야 한다.

#### 원칙 4 — 색+글자+아이콘 병기

- 10종 배지에 세 요소를 모두 같은 강도로 넣으면 표가 과밀해진다.
- 글자를 주 정보로 두고 색과 아이콘은 보조로 써야 한다. 장식 아이콘은 스크린리더에서 중복 낭독되지 않게 처리한다.

#### 원칙 5 — 전역 상태줄

- 세로 공간, 과도한 폴링, 상태 변화의 반복 낭독이 부작용이다.
- 28~32px 단일 행으로 제한하고, 상세 내용은 눌러서 열게 한다.
- 여러 화면이 각각 상태 API를 폴링하지 말고 renderer의 중앙 상태 저장소에서 갱신 주기·최신 시각을 관리해야 한다.
- 스크린리더 알림은 매 폴링이 아니라 상태가 실제로 바뀌었을 때만 발생해야 한다.

#### 원칙 6 — 상태를 데이터 신원에 묶기

- `유효 목록에 없으면 자동으로 바꾼다`는 규칙은 가장 위험하다. 사용자가 모르는 사이 다른 근무유형으로 바뀌어 저장될 수 있다.
- 자동 교체하지 말고 `현재 설정에서 사용할 수 없는 값`으로 표시한 뒤 사용자가 다시 선택하게 해야 한다.
- ID 결합만으로는 늦은 비동기 응답, 저장 전 초안, undo 분기, 같은 ID 재조회 문제를 막지 못한다.

### 3. 구조 선택(A/B/C): **A안 지지**

최신 사용자 결정인 A안을 지지한다.

- P1을 가장 직접적으로 해결하며 준비→운영→정산의 업무 흐름을 화면 구조에 반영한다.
- 기존 8개 메뉴 이름은 그룹 안에서 그대로 유지하고, 사용자가 홈을 거치지 않아도 각 화면에 직접 들어갈 수 있어야 한다.
- Claude의 C안은 안전한 기본안이지만 `메뉴 변경 시 문의가 늘어난다`는 판단도 운영자 관찰로 검증된 사실은 아니므로 결정적 근거는 아니다.

단, 홈의 `준비/운영/정산 진행 막대`는 완료 조건과 데이터 출처를 먼저 정의해야 한다. 예를 들어 승인대기 건수는 어느 API, 미배포 판정은 어느 목록·이력 조합으로 계산하는지 명세가 있어야 한다. 계산 정의가 없는 진행률은 가짜 UI다.

### 4. 밀도 선택(V1/V2/V3): **V3 기본 + V1 좁게 모드 지지**

사용자가 선택한 V3를 기본값으로 지지한다. 32px 좁게 모드도 유지할 수 있다.

산술은 맞다.

- `700 ÷ 32 = 21.875` → 완전히 보이는 행 약 21개
- `700 ÷ 36 = 19.444` → 약 19개
- `700 ÷ 40 = 17.5` → 약 17개

하지만 700px이라는 전제가 불완전하다. 새 전역 상태줄, 가로 스크롤바, 그룹 머리, Windows 창 장식이 빠져 있다. 상태줄 32px와 가로 스크롤바 약 12px만 빼도 `656 ÷ 40 = 16.4`이므로 실제 완전 표시 행은 약 16개이고 그룹 머리가 끼면 15개까지 내려갈 수 있다.

따라서 문서에는 `약 17행 목표, 목업·실앱에서 실측`이라고 적어야 한다. 사유 칩도 40px 안에서 한 줄 말줄임이 가능해야 하며 긴 설명 때문에 행 높이가 가변으로 변하면 가상 스크롤 계산이 깨질 수 있다.

### 5. 가장 먼저 깨질 지점

**근무지 마법사에서 늦게 도착한 비동기 응답이 다른 편집 초안에 섞이는 문제**가 가장 먼저 재발할 가능성이 높다.

예상 시나리오:

1. 근무지 A에서 기존 엑셀 패턴 역추출을 시작한다.
2. 완료 전에 근무지 B를 열거나 A를 다시 연다.
3. A의 응답이 늦게 도착해 현재 화면의 B 초안에 반영된다.
4. 없어진 근무유형을 자동 교체하는 로직까지 실행된다.
5. 사용자는 B의 설정으로 알고 저장하지만 A에서 온 일부 상태가 섞여 저장된다.

데이터 신원 결합만으로는 이 흐름을 막을 수 없다. 요청 세대번호 또는 취소 토큰으로 현재 초안과 일치하지 않는 응답을 폐기해야 한다.

### 추가 — 근무지 마법사

원칙 6만으로 재발을 막을 수 없다. 최소한 다음을 설계 원칙 또는 수용 기준에 추가해야 한다.

- 저장된 데이터와 편집 초안을 별도 상태로 관리
- 화면 진입·데이터 로드만으로 저장 대상 데이터 변경 금지
- `dirty` 표시와 화면 이탈 확인
- 비동기 요청별 세대번호/취소 처리 및 늦은 응답 폐기
- 유효하지 않은 선택값 자동 교체 금지
- 상태 전이를 순수 함수 또는 reducer로 집중
- undo 기록에 데이터 신원·기준 버전·전/후 상태를 포함하고 기록 개수를 제한
- 저장→재조회 왕복 테스트
- 시뮬레이션 달력과 실제 근무표 패리티 테스트
- 실제 렌더링 환경에서 클릭 가로채기·겹침·포커스 순서 E2E 테스트

### 추가 — 실적 관리 화면 분할 여부

**상위 메뉴는 하나로 유지하되, 화면 내부 작업공간은 분할해야 한다.** 별도 최상위 메뉴로 쪼개면 한 업무의 맥락이 끊기지만 모든 영역을 동시에 펼치면 정보 과부하와 세로 공간 손실이 발생한다.

권장 구성:

1. **접수·복구**
   - 폴더 감시, 인테이크 진행, 해석 실패, 시작 복구, 고아 승인 상태
2. **승인 작업**
   - 승인대기 파일, 근무지별 그룹, 가상 스크롤 표, 행 상세
3. **재승인·비교**
   - 기존 승인행과 수정행 비교, 재승인본 확정, 관련 이력

공통 기간·근무지 필터는 세 작업공간에서 유지한다. 정상 상태의 인테이크 영역은 상단 한 줄 요약으로 접고, 오류가 있을 때만 확장해야 한다. 승인 후에는 다음 행으로 포커스를 예측 가능하게 이동하고 현재 선택·스크롤 위치를 보존해야 한다.

### 절대 규칙 위반 여부

현재 초안에 확정 위반은 없지만 아래 두 항목은 그대로 구현하면 절대 규칙 위반이 될 가능성이 높다.

1. **유효하지 않은 선택값 자동 교체**
   - 사용자에게 알리지 않은 데이터 변경이며 `데이터를 조용히 잘라내거나 바꾸지 않는다`는 원칙 및 P6 재발 방지 취지와 충돌한다.

2. **정의되지 않은 홈 진행 막대·할 일 건수**
   - 실제 데이터 출처와 계산 규칙이 없으면 가짜 UI다.

다음 항목은 위 수정 조건 아래 절대 규칙과 양립 가능하다.

- A안 메뉴 구조
- V3/V1 밀도 토글
- 실적 관리 화면 내부 분할
- 전역 상태줄
- 사유 칩과 확인 모달

이 검토는 화면 설계에 한정한다. 이관 코드, DB 스키마, 승인·계산 트랜잭션, forward-only 규칙, 엑셀 행 순서, 게시 절차를 변경하라는 제안은 없다.
