## 2. Blocking defect C4 — font 변경을 속성별 delta가 아니라 전체 font 객체로 덮는다

### 2.1 독립 실제 XLSX 재현

기본 `proposal-xlsx` 정의에서 `proposal.regular-summary.font.bold`만 `true`로 바꿨다. candidate에는 기본 정의가 가진 `family="맑은 고딕"`, `sizePt=11`도 그대로 존재하지만 사용자가 바꾼 속성은 `bold` 하나뿐이다.

```text
validateDocumentLayoutDefinition(..., "preview") issue = []
computeBlockDelta(...).fontChanged = true

기본 preview:
B18 font.size = 12
E19 font.size = 9
D18 style = {}

bold만 변경한 실제 preview XLSX 재로딩:
B18 font.size = 11, bold = true
E19 font.size = 11, bold = true
D18 style에 font{name="맑은 고딕", size=11, bold=true}와 기본 border/fill 생성
```

즉 bold 변경은 성공했지만 사용자가 건드리지 않은 `sizePt`까지 11로 평탄화했다. 이는 1차 교정 지시의 “candidate와 baseline의 **속성별 delta만** override”를 충족하지 않는다.

### 2.2 원인

`computeBlockDelta`는 font 객체 전체를 `JSON.stringify`로 비교해 `fontChanged: boolean`만 만든다. 이후 renderer는 `fontChanged`가 true이면 candidate font에 존재하는 family/size/bold/italic/color를 전부 모든 셀에 적용한다.

따라서:

- 한 속성 변경이 다른 font 속성을 덮는다.
- 같은 의미의 font 객체라도 key 삽입 순서가 다르면 변경으로 오인할 수 있다.
- block 내부의 의도적인 9pt/12pt 혼합 서식이 다시 손실된다.

### 2.3 필수 교정

1. `fontChanged: boolean`만 사용하지 말고 `family`, `sizePt`, `bold`, `italic`, `color`별 semantic delta를 계산한다.
2. baseline과 값이 다른 속성만 실제 셀 font에 적용한다.
3. candidate에 font 객체가 있어도 baseline과 의미상 같으면 rebuild/override하지 않는다. 객체 key 순서는 무관해야 한다.
4. candidate 속성이 `undefined`인 현재 계약은 기존 동작처럼 “추가 override 없음”으로 취급한다. bold 해제는 `false`처럼 명시 값으로 표현한다.
5. `hasDocumentLayoutModifications`와 `computeBlockDelta`가 같은 semantic 비교 규칙을 사용하게 한다.

필수 관찰값:

```text
regular-summary bold=true만 변경 후
B18: size 12 유지, bold true
E19: size 9 유지, bold true
D18: size/name을 새로 만들지 않음; bold 적용에 필요한 최소 font delta만 존재
```

같은 font 값을 key 순서만 바꾼 정의는 `hasDocumentLayoutModifications=false`이고 workbook 변화 0이어야 한다.
