## 4. Sol의 잠근 상태 전이와 파일별 코드 전략

데이터 정본은 `window.appBridge.changePassword`와 `getSession`의 서버 응답이다. 화면 상태 `idle / checking / limited / loginChosen / accepted`와 `postChangeGeneration`은 UI 요청의 소유권만 나타낸다. 화면 표시만으로 인증을 승인하거나 `passwordChangeRequired`를 무시하지 않는다.

1. **시험 먼저 — `login.mjs`.** 새 `--case=post-change-first-held`를 추가한다. 기존 격리 데이터·bootstrap 사전 검문 후 관리자를 L1→L4로 로그인한다. `auth:change-password` 요청을 계수하고 **첫 요청만 실제 서버로 통과**시킨다. 두 번째 요청이 발생하면 서버에 전달하지 않고 테스트 응답으로 막되 계수해 RED로 표시한다. 첫 변경 뒤 **첫 `auth:get-session`**을 Promise gate로 보류하고 요청 시작을 확인한다. 보류 중 편집 필드 3개와 `#l4-btn-submit`이 없고 확인 중 안내와 L1 이동 버튼이 있는지 검사한다. 기존 코드의 폼이 보이면 유효한 두 번째 입력·클릭을 시도해 두 번째 요청을 계수하고 의도한 RED manifest를 남긴다. 이때 비밀값은 로그·캡처·manifest에 넣지 않는다. GREEN에서는 마우스·Enter·Tab 조작 뒤에도 계수 1이어야 한다. 응답을 풀어 실제 서버 세션으로 셸에 진입하고 다시 계수 1을 확인한다. 실패 시에도 gate를 해제해 정리한다. 고정 시간 sleep으로 경합을 만들지 않는다.
2. **제품 전이 — `login.ts`.** `renderL4`가 `checking`이면 오류 문구와 무관하게 편집 폼을 렌더하지 않는다. 변경 성공 분기에서 `checking`·세대 증가·오류 문구 초기화 후 **동기적으로 `render()`**하여 폼을 제거하고, 그 다음 `verifyPostChangeSession(currentGen)`을 호출한다. 변경 제출 핸들러에도 `idle` 상태만 변경 요청을 시작할 수 있는 방어 가드를 둔다. 변경 요청의 실패/결과 불명 분기에서는 기존 L4 오류 경로를 유지하고 완료를 단정하지 않는다. 기존 `isSubmitting`은 로그인 제출과 충돌시키지 않으며, 변경 성공 대기 상태를 공용 불리언만으로 표현하지 않는다.
3. **확인 중·실패 화면 — `login.ts`.** 기존 `session-verify-container`를 재사용하거나 작은 분기 hunk로 확인 중 화면을 만든다. 초기 `checking`에는 “비밀번호가 변경되었습니다. 세션 확인 중…”에 해당하는 사실 문구, 진행 상태, `로그인 화면으로 이동`만 보인다. 확인 실패를 뜻하는 경고 문구나 활성 재확인 버튼을 조기에 보여주지 않는다. `limited`에는 기존 실패 안내·`세션 다시 확인`·L1 버튼을 보여준다. 실패 뒤 재시도 중에도 편집 폼은 절대 복귀하지 않는다. L1 선택은 현재 요청 세대를 즉시 무효화하고 완료 안내를 남긴다. 늦은 응답의 성공/null/오류/catch/finally는 현재 세대·`checking`·L4 여부 검사에서 탈락하면 화면과 제출 상태를 바꾸지 않는다.
4. **기존 경합 계측 — `login.mjs`.** `post-change-race-login`에서 `signInRequested` 단일 불리언을 요청 횟수 계수로 바꾼다. 최초 관리자 요청 완료 뒤 기준 계수를 기록하고, 지연된 두 번째 `getSession`이 풀리기 전 새 L1 제출로 계수가 **정확히 1 증가**했음을 확인한다. 최초 요청만으로 PASS가 되지 않게 한다. 나머지 3개 경합 사례의 늦은 응답·L1 입력·배너 단언을 유지한다.
5. **셸 시험 대기 — `shell.mjs`.** `#sb-pending`의 텍스트가 숫자 `대기 파일: N개`가 될 때까지 Playwright의 조건 대기를 최대 15초 사용한다. 시간 초과 시 마지막 UI 문구를 담아 FAIL. 그 후 기존 `listPendingFiles` 직접 API 조회와 정확한 count 비교를 그대로 수행한다. `확인 실패`, 정체된 값, API 실패, 값 불일치는 FAIL이다. `statusBar.refresh()`만 기다리는 방식은 `isFetching`일 때 바로 반환하므로 완료 보증으로 사용하지 않는다. 고정 sleep·반복해서 우연히 같은 수치 찾기 금지.

최소 hunk만 바꾸고 인코딩·줄바꿈·타 파일을 건드리지 않는다. 기존 R31-RACE-01~05의 보증을 재검증한다. 지난 2회 CORRECT와 R1 실패 이력은 리셋되지 않는다.

### 6.3 실제 Chrome 실행

최종 사례는 기존 8개 `ready`, `login flow/locked/recovery/session-error/post-change-null/post-change-error`, `shell` + 기존 경합 4개 `post-change-race-success/null/error/login` + 신규 `post-change-first-held` = **13개**다. 각 최종 manifest는 PASS, 캡처 실제 파일 존재, 콘솔·페이지·요청 실패·HTTP 400+ 0이어야 한다. 비밀번호가 입력된 화면은 캡처하지 않는다. 새 사례의 확인 중 화면과 정상 셸, 경합 4개 L1 화면 및 셸 상태줄을 실제 클릭·키보드·캡처로 확인한다. 셸은 56px 헤더·32px 상태줄·220↔64px 사이드바 및 5개 API 값 대조를 그대로 유지한다.

## 8. 착수 게이트·회신 증거

착수 전에 `git rev-parse --abbrev-ref HEAD`, `git rev-parse HEAD`, `git status --short --untracked-files=all`, 부록 A 각 경로 SHA를 직접 확인한다. 상태 87줄은 LF 결합·끝 LF 없는 UTF-8 SHA와 일치해야 한다. 허용 3파일은 위 시작 SHA와 같아야 한다. 예상 밖 파일이 하나라도 있으면 수정하지 않는다.

`## 회신`에는 판정, 기준·초기 87경로 해시/부록 A 대조, 3파일 전후 SHA·전후 diff, R31-R2-01~08 구현 위치, N-R2-01~05 결과, 명령별 RC·실제 시험 수·시각, RED 및 13 최종 manifest의 **실제 경로**와 PASS/FAIL·Chrome/viewport/격리 폴더·콘솔/페이지/요청/HTTP 오류 수, **각 manifest에 기록된 실제 캡처 파일명**, 모든 중간 FAIL의 경로·메시지·해소 근거, `signIn` 초기/새 요청 계수와 `changePassword` 계수, 84 보호 경로 불변·범위 밖 변경 0, 정리 결과와 미해결을 적는다. 미래 파일명을 추정해 쓰지 않는다. manifest를 파일시스템에서 전수 검색해 제출하며 FAIL 1건이라도 누락하면 `FAILED`다.
