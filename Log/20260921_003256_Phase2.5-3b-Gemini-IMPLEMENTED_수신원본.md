### 3.1 좌표 충돌의 현재 구현 결정

명세 v1.0 §3.1의 1-based 문장과 달리, 이미 발송·수락·종결된 3a 구현 계약과 실제 기본 정의는 **0-based**다. 이번 작업에서 다시 뒤집지 않는다.

- `x=0, y=0`은 Excel `A1`이다.
- `width`, `height`는 차지하는 열·행 수다.
- ExcelJS 셀 경계에서만 각각 `+1`해 1-based로 바꾼다.
- 정수 아닌 `x/y/width/height`는 renderer에 넘기지 말고 검증 오류로 거절한다.
- 캔버스 경계는 현재 3a와 같이 `x + width <= canvas.width`, `y + height <= canvas.height`다.

### 3.2 레이아웃 입력의 단일성

- 저수준 내장 JSON은 값·서식·병합·행 높이의 **보호된 원형**이다.
- 고수준 `DocumentLayoutDefinition`은 사용자가 허용 범위 안에서 바꾼 **실행 레이아웃**이다.
- 운영 출력: `getDocumentLayout(key).definition`을 사용한다.
- 초안 미리보기: 전달받은 definition을 `preview` 모드로 검증하고 사용한다. 저장하거나 활성 판을 바꾸지 않는다.
- 기존 `DocumentTemplateVersion.sourcePath`, 등록 workbook, `document-template-preview-service.ts`는 생성 입력으로 사용하지 않는다.
- 기존 legacy template/profile은 변형 식별의 하위 호환 근거가 꼭 필요한 곳에서만 읽을 수 있고, 셀 값·서식·파일 경로를 출력에 덮어쓰면 안 된다.

## 4. 필수 설계 결정

### D1. 실제 생성 함수 하나

운영과 미리보기는 다음 실제 writer를 공유한다.

- 근무표: `writeSchedulePlanWorkbook`의 레이아웃 인식 경로
- 수당 XLSX: `writeUpdatedProposalWorkbook`, `writeAttachmentOneWorkbook`, `writeAttachmentTwoWorkbook`이 사용하는 공용 내부 렌더 경로

미리보기 서비스가 ExcelJS workbook을 별도로 새로 만들거나 셀을 다시 흉내 내면 실패다. 실제 writer에 `definition`, 결정적 데이터, 출력 경로를 주입하는 얇은 조정자여야 한다.

### D2. 레이아웃 적용 경계

새 `document-layout-excel-render-service.ts`를 레이아웃 해석의 단일 경계로 둔다. 구현 기법은 선택할 수 있으나 아래 관찰 계약은 고정이다.

- 모든 블록을 내장 기본 정의의 같은 ID와 대응시킨다.
- 이동은 0-based 후보 좌표를 ExcelJS 1-based 좌표로 정확히 변환한다.
- 동적 행이 있는 품의서·별첨1·별첨2는 명세의 `R`, `E`, `N`, `X`, 근무지별 소계 수에 따라 실제 블록 범위를 계산한다. 기본 정의의 표본 높이를 고정 실제 높이로 오해하지 않는다.
- 동적 앞 블록 때문에 뒤 블록이 밀리는 값은 현재 생성기의 계산식을 보존하면서 후보 기준 위치에 더한다.
- 병합 토폴로지, 데이터 바인딩, 값 순서, 행 순서, 행 높이, 숫자 형식, 테두리, 채움은 사용자 속성이 아니다. 위치/크기에 따라 생성기가 절대 좌표를 다시 계산할 수는 있지만 사용자가 병합 목록을 주입할 수는 없다.
- post-render 이동 방식이면 모든 원본 블록의 값·스타일·병합·이미지를 먼저 캡처한 뒤 원본을 지우고 배치한다. 앞 블록 이동이 뒤 블록 원본을 덮어쓰는 순차 복사는 금지다.
- valid candidate의 허용 속성을 조용히 무시하거나 잘라내지 않는다. 보호 구조를 보존해 표현할 수 없는 geometry는 파일 쓰기 전에 한국어 validation issue로 거절한다.
- 보이는 블록끼리 최종 실제 범위가 겹치면 거절한다. `schedule.month-anchors`는 보호 metadata라 시각 충돌 계산과 이동 대상에서 제외하되 값·위치는 보존한다.
- `visible=false`는 행/열 전체 숨김이 아니다. 그 블록의 값·서식·병합·이미지만 출력에서 제외해 다른 블록을 숨기지 않는다.

### D3. 크기 변경의 최소 수용 기준

- `size`를 capability에 노출한 뒤 무시할 수 없다.
- 정적 제목/설명/필드/요약/바닥글, 로고, 일반 표 각각에서 적어도 한 대표 블록의 확대 또는 축소를 실제 파일로 검증한다.
- 동적 표의 실제 높이는 `candidate.height + 동적 추가 행` 의미를 갖거나 같은 결과를 내는 명시적 document-specific plan을 쓴다.
- 보호 내부 구조를 손실 없이 표현할 수 없는 크기는 `UNRENDERABLE_BLOCK_SIZE` 같은 안정적 code와 한국어 message로 preview/save 모두 거절한다.
- 기본 크기 결과는 기존과 같아야 한다.

### D4. 열 너비 키

`columnWidths` 키는 블록에 대한 **상대 Excel 열 글자**로 고정한다.

- 첫 열 `A`, 다음 `B`, 27번째 `AA`; 대문자 canonical 형식만 허용한다.
- 상대 열 번호가 후보 블록 `width`를 벗어나면 거절한다.
- 값은 ExcelJS `column.width`의 양의 유한수다.
- 이동한 블록에서도 `A`는 새 블록의 첫 열이다.
- 서로 다른 보이는 블록이 같은 실제 열에 상충 너비를 지정하면 `CONFLICTING_COLUMN_WIDTH`로 거절한다.

### D5. 글꼴·문구·로고·표시

- `font`는 블록의 값/서식 셀에 family/size/bold/italic/color만 덮어쓰고 숫자 형식·정렬·테두리·채움·보호는 보존한다.
- 정적 문구 블록의 `text`는 기존 정적 값 앵커에 쓴다. 바인딩 블록 값은 definition text로 바꿀 수 없다.
- 현재 자산 레지스트리는 `brand-logo` 하나다. `logoAssetId`는 `"brand-logo"`, `null`만 renderable하다. 알 수 없는 ID는 preview/save 모두 거절한다.
- `null` 또는 `visible=false`이면 이미지를 만들지 않는다. 로고는 후보 범위의 `oneCell` 경계에 맞춘다.

### D6. 파일명 패턴

3b부터 XLSX 운영 출력과 내부 미리보기는 `outputs[0].outputFileNamePattern`을 실제 사용한다.

- Excel 문서는 `.xlsx`로 끝나야 한다.
- schedule token: `{year}`, `{monthNumber}`, `{month2}`, `{siteName}`
- allowance token: `{year}`, `{month2}`
- 토큰 값의 Windows 금지 문자·경로 구분자는 안전한 문자로 치환한다.
- 패턴의 `/`는 base directory 아래 하위 폴더다. `path.resolve` 결과가 base 밖이면 거절한다.
- 기본 근무표 예: `2026년/5월/2026_5_미리보기근무지.xlsx`
- 기본 수당 예: `2026년/05월/2026_05_품의서.xlsx`
- 중복은 확장자 앞 `_dup01`, `_dup02`다. 현 `_1`, `_2`를 새 XLSX 경로에 남기지 않는다.
- 근무표의 기존 year/month 폴더와 definition 패턴을 중복 적용하지 않는다.
- PDF 경로는 바꾸지 않는다.

### D7. 내부 미리보기 서비스

새 `document-layout-preview-service.ts`는 공개 bridge 타입을 구현하지 않고 다음 내부 책임만 가진다.

- 입력: Excel 5키 중 하나의 draft definition, 호출자가 소유한 `outputDir`
- 처리: `validateDocumentLayoutDefinition(draft, "preview")` → 결정적 fixture → 실제 writer
- 성공: `memberId`, XLSX media type, 실제 `filePath`, 상대 `fileName`의 내부 artifact 목록
- 검증 실패: 파일/폴더/DB 행을 만들지 않고 issues를 반환하거나 문서화된 내부 오류를 던진다. 반쪽 파일을 남기지 않는다.
- save/reset/history를 호출하지 않고 업무 DB의 근무표·직원·실적·계산·승인·근무지 데이터를 읽지 않는다.
- `previewId`, URL, 만료는 3c가 이 결과를 감싼다.

결정적 fixture 의미:

- 기준 월 `2026-05`, 고정 시각 `2026-05-01T00:00:00.000Z`
- schedule: 근무지 `미리보기근무지`, D/E/N/O 달력 값과 정규/변경·대체·연장 예시 모두 포함
- allowance: 유효 가상 사번만 사용하고 정규/조기, 2개 이상 근무지, 대체/연장/법정공휴일 금액 모두 포함
- Pool, BP, 사번 없는 비BP를 미리보기 지급 행으로 만들지 않는다.
- 같은 definition을 서로 다른 빈 디렉터리에 두 번 생성하면 workbook의 의미상 셀/병합/서식/이미지 snapshot이 같다. ZIP timestamp raw bytes만 비교하지 않는다.

### D8. 운영 출력 연결

- `exportMonthlySchedulePlan`은 variant 확정 뒤 해당 `getDocumentLayout` snapshot을 읽어 filename과 writer에 같은 definition을 전달한다.
- XLSX `exportAllowanceDocuments`는 세 key snapshot을 먼저 읽고 filename과 writer에 각각 전달한다.
- PDF branch는 3b layout service를 호출하지 않는다.
- 저장본이 없으면 built-in fallback, malformed/복수 active/키 불일치는 명확히 실패하며 조용히 폴백하지 않는다.
- 출력 이력의 optional legacy template ID 때문에 schema를 바꾸지 않는다. layout revision ID 저장은 후속 설계 전 추가하지 않는다.
- legacy `sourcePath` 누락/파손에도 XLSX는 성공하고 legacy style/profile 변경이 새 출력 레이아웃을 덮어쓰지 않는다.

## 7. 구현 순서

1. 착수 게이트와 SHA/status를 기록한다.
2. definition validator에 D3~D6 렌더 가능성 반례를 추가한다. canonical block ID/순서/capability는 바꾸지 않는다.
3. filename/token/geometry plan과 ExcelJS 적용 경계를 신규 render service에 만든다.
4. 근무표 actual writer에 연결하고 기본 정의 parity를 먼저 닫는다.
5. 품의서·별첨1·별첨2 actual writer에 연결하고 동적 범위를 닫는다.
6. 운영 export 두 경로가 snapshot과 pattern을 쓰게 한다.
7. 결정적 preview service를 actual writer 위에 얹는다.
8. 집중 시험 → 전체 게이트 → 최종 status/SHA를 기록한다.

대형 파일을 이유 없이 전면 재작성하지 않는다. allowance service의 지급 대상 선별·금액 계산·병합 복구는 레이아웃 연결에 필요한 최소 변경만 한다.

## 8. 필수 시험 행렬

### 8.1 definition/render

1. 5개 기본 정의가 preview/save/renderability 검증을 통과한다.
2. 소수/NaN/Infinity geometry를 거절한다.
3. 상대 열 `A`, `B`, `AA` 정상과 소문자·범위 밖·잘못된 키 반례를 검증한다.
4. 알 수 없는 logo ID와 Excel이 아닌 확장자를 거절한다.
5. 보이는 블록 충돌, 동적 실제 범위 충돌, 동일 실제 열의 상충 width를 거절한다.
6. schedule metadata는 불변이며 시각 충돌 오탐이 없다.
7. 기본 actual output이 셀 값·병합·폭·높이·글꼴·정렬·테두리·채움·숫자 형식·worksheet 설정에서 기존과 같다.
8. 대표 정적 블록/표의 position/size/visibility/text/font/columnWidths, 로고 position/size/null이 파일 재로딩 뒤 관찰된다.
9. 이동 순서 때문에 다른 블록 값·병합·스타일이 사라지지 않는다.

### 8.2 실제 writer/운영 출력

1. schedule template1/template2 기본 fallback 회귀
2. 활성 저장본 제목 이동·문구·글꼴·표 열 너비·visibility 반영
3. schedule filename token과 `_dup01`
4. proposal 정규 0/1/여러 근무지 × 조기 0/1/여러 근무지 동적 범위·병합
5. attachment1 정규/조기 상세·소계·합계·22행 요율 안내와 단일 시트
6. attachment2 여러 근무지·소계·합계 실제 끝행
7. 세 수당 문서의 서로 다른 저장 definition/pattern
8. legacy sourcePath 누락/파손과 legacy style 변경의 무영향
9. PDF branch 기존 계약 불변
10. Pool/BP/사번 없는 비BP 지급 행 0, 유효 사번 대상 양성

### 8.3 내부 미리보기

1. Excel 5키 각각 열 수 있는 XLSX 한 개
2. draft 변경이 운영과 같은 writer를 거쳐 반영
3. schedule parser table 이동은 preview 생성, save 차단 유지
4. 같은 draft 두 번의 의미상 snapshot 동일
5. invalid draft 산출물/저장 row/active revision 변화 0
6. 미리보기 전후 업무 표 행 수·canonical hash 동일; 가능하면 storage 미호출 spy
7. old preview/sample/sourcePath 미호출
8. outputDir 밖 쓰기 0, temp 정리

기존 시험은 삭제·skip·완화하지 않는다. legacy style 기대 변경은 같은 시험에서 “새 layout만 영향, legacy 값은 무영향”을 더 강하게 증명한다.
