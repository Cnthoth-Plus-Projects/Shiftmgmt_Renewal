### 6.3 승인 count 세부 계약

1. `remainingPayableRows`와 그 ID set을 만든다.
2. 해당 file의 approval history 행 전체를 최신순으로 읽는다.
3. entry ID별 최신 행 하나만 남긴다.
4. 최신 decision이 정확히 `approved`이고 entry ID가 remaining payable ID set에 있을 때만 센다.
5. 해당 file의 approval history 행 자체가 0개일 때만 legacy metadata fallback을 사용한다.
6. 승인 이력은 있으나 전부 최신 rejected이거나 non-payable/orphan ID뿐이면 결과는 0이다.
7. `approved_entry_count <= entry_count`가 항상 성립해야 한다.

- JSON 삭제는 V4 격리 target에서만 하며 원본 JSON과 V3는 읽기 전용이다.
- 연결 승인·숨김·직접 계산·승인 연결 계산이 있는 삭제 후보는 fail-closed한다.
- preview 모호성은 추정하지 않고 전체 rollback한다.
- 기존 계산 263건/56,076,024원과 승인 완료 계산 64건/13,611,839원을 보존한다.
- `row_count`, `file_size`는 내용 메타데이터가 아니라 원본 파일 물리 정보이므로 유지한다.

### 7.2 반드시 피할 과거 실패

- 남은 모든 행 수를 approved count로 복사하지 않는다.
- `COUNT(DISTINCT ... approved)`로 “한 번이라도 승인”된 ID를 세지 않는다.
- non-payable 승인 이력을 승인 진행 count에 넣지 않는다.
- 최신 rejected가 있는데 metadata fallback으로 과거 승인 수를 되살리지 않는다.
- `warning_count`라는 컬럼명만 보고 severity warning만 세지 않는다. 현재 producer의 실제 의미를 따른다.
- full suite 실패를 “범위 밖 시험”으로 남겨 `CORRECTED`를 선언하지 않는다.
- 해시나 테스트 수를 추정해 쓰지 말고 명령 원문으로 측정한다.
