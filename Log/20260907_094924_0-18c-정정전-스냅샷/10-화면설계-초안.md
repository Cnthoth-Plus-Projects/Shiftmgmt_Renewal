## 3. 설계 원칙 8개

v0.1의 6개를 **Codex 지적에 따라 전면 수정**하고 2개를 추가했다.

### 원칙 1. 조치 가능한 0에만 이유를 붙인다 (수정됨)

> **v0.1**: "빈 값·0에는 반드시 이유를 붙인다"
> **v0.3**: 정상적인 0까지 전부 설명하면 표가 사유 문구로 뒤덮인다. **조치 가능한 것만** 강조한다.

| 구분 | 처리 |
|---|---|
| **업무상 이상하거나 조치 가능한 0** | 값 옆에 **한 줄 사유 칩**. 필요하면 다음 행동 버튼 |
| **정상적인 0** (예: 그 날 연장근무가 원래 없음) | 표에는 `0`만. 이유는 **행 상세·도움말**에서 |

🔴 **이유를 화면이 추정해서 만들지 않는다.** 내부 계산이 돌려준 사유 코드나 코드로 확정 가능한 사유만 쓴다. 화면이 "아마 이래서 0일 것"이라고 짐작해 문구를 만들면 그 자체가 새로운 사고다.

```
좋음:  수당 0원 [지급 대상 아님 — 대체 투입자가 주간고정조]   ← 내부 계산이 사유 코드를 돌려줌
좋음:  근무시간 0분 [8월 근무표 없음] + [8월 근무표 만들기]
나쁨:  수당 0원 [아마 정책 때문인 듯]                        ← 화면이 지어낸 이유
```

**사유 칩 제약**: 행 높이 40px 안에서 **한 줄 말줄임**이 가능해야 한다. 긴 설명 때문에 행 높이가 들쭉날쭉해지면 표 성능 처리(가상 스크롤)가 깨진다. 전문은 마우스를 올리거나 행 상세에서 본다.

### 원칙 2. 확인창은 4종, 빨강은 파괴적 동작에만 (수정됨)

> **v0.1**: 되돌릴 수 없는 동작 5개를 전부 같은 위험 확인창(빨강)으로
> **v0.3**: 확인 피로를 막고, 빨강의 의미를 지킨다

| 종류 | 언제 | 버튼 | 보여줄 것 |
|---|---|---|---|
| ① 단순 확인 | **되돌릴 수 있지만 작업 내용이 사라지는** 경우로 제한 | 기본 | 한 줄 |
| ② 위험 확인 (강조) | **실적 승인 · 품의 승인 · 근무표 게시** | 파랑 강조 | 대상 **건수·금액·기간**, "되돌릴 수 있는지", **실행 후 무슨 일이 벌어지는지** |
| ③ 파괴 확인 (빨강) | **삭제 · 데이터베이스 교체** | **빨강** | ②의 내용 + 되돌릴 수 없음 명시 |
| ④ 사유 입력 | 반려 · 승인 되돌리기 | 기본 | ②의 내용 + 사유 입력칸(필수) |

- 되돌릴 수 있고 잃을 것도 없는 동작에는 **확인창을 띄우지 않는다.** (확인 피로 → 안 읽고 누름 → 사고)
- **실행이 시작된 뒤에는 Esc로 닫히지 않고 재실행도 안 된다.** 진행 표시만 보인다.

### 원칙 3. 권한 없는 버튼은 "포커스는 가되 눌리지 않게" (수정됨)

> **v0.1**: 비활성 + 마우스 올리면 이유 툴팁
> **v0.3**: 그렇게 하면 **키보드·화면 낭독기 사용자는 이유를 영영 모른다.** 일반적인 비활성 버튼은 키보드 포커스를 받지 못하기 때문이다.

- 포커스는 받되 눌리지 않는 방식(`aria-disabled`)을 쓰거나, **버튼 옆에 항상 보이는 설명**을 둔다.
- **적용 범위**: 지금 권한으로 **들어갈 수 있는 화면 안의 작업 버튼**에만 적용한다. 관리자 전용 화면(운영 관리·활동 이력) 자체는 메뉴에서 안 보이는 게 맞다.

### 원칙 4. 글자가 주인공, 색과 아이콘은 거들기 (수정됨)

> **v0.1**: 색 + 글자 + 아이콘을 함께
> **v0.3**: 배지 10종에 셋을 같은 세기로 넣으면 표가 과밀해진다.

- **글자가 주 정보.** 색과 아이콘은 보조.
- 흑백으로 만들어도 구분되면 통과 — 이 기준은 유지.
- 장식용 아이콘은 **화면 낭독기가 중복해서 읽지 않도록** 처리한다.

### 원칙 5. 전역 상태줄 — 한 줄, 중앙 관리, 역할별로 다르게 (수정됨)

- 창 하단 전체 폭 **32px 한 줄 고정.** 상세는 눌러서 연다.
- 🔴 **화면마다 각자 상태를 물어보지 않는다.** 한 곳(중앙 상태 저장소)에서 갱신 주기와 최신 시각을 관리하고, 각 화면은 거기서 읽어 쓴다.
- 🔴 화면 낭독기 알림은 **상태가 실제로 바뀌었을 때만.** 갱신할 때마다 읽으면 소음이 된다.

🔴 **역할별로 보이는 칸이 다르다** (코드 검증 결과 — `12-능력-매트릭스.md` §4)

| 칸 | 일반 사용자·계획·승인 담당 | 관리자 |
|---|---|---|
| DB 연결 | ✅ | ✅ |
| **최근 인테이크** (`처리 이력 없음`/`읽는 중 34/120`/`해석 중`/`마지막 처리 완료 14:32`/`오류 1건`) | ✅ | ✅ |
| **대기 파일 N개** (파일 수. 실적 행 수는 `대기 실적 N건`으로 따로 씀) | ✅ | ✅ |
| **폴더 감시 실행 여부** | ❌ **불가** | ✅ + `[다시 시작]` |
| 업데이트 | ✅ | ✅ |

**왜**: 폴더 감시 실행 여부는 관리자 전용 창구(`operations:get-file-watch-status`)에만 있다. `app:get-health`에는 그 값이 없다. 그래서 기본 칸을 `폴더 감시 중` → **`인테이크 상태`** 로 바꿨다. 전 역할이 볼 수 있고, 실사용자가 실제로 궁금해하는 "내 파일 읽혔나?"에 더 가깝다.

### 원칙 6. 화면 상태는 데이터 신원에 묶되, 값을 몰래 바꾸지 않는다 (중요 수정)

> **v0.1**: "선택값은 현재 유효 목록과 대조해 **자동 교체**한다"
> **v0.3**: 🔴 **자동 교체 금지.** 이것이 Codex가 지적한 가장 큰 위험이었다.

**왜 뒤집었나**: 사용자가 모르는 사이에 다른 근무유형으로 바뀌어 저장될 수 있다. 이 프로젝트에는 **"데이터를 조용히 잘라내거나 바꾸지 않는다"** 는 절대 규칙(`07` A-5)이 있다. 자동 교체는 그 규칙을 정면으로 어긴다.

> ⚠️ 참고: `07` B-2는 이 사고의 대응책을 "자동 교체"라고 적어 뒀다. 하지만 그 문장의 취지는 *"못 쓰는 값이 선택된 채 남아 저장되면 안 된다"* 이지 *"몰래 바꿔라"* 가 아니다. 절대 규칙(A-5)이 우선하므로 아래처럼 고친다.

| 상황 | v0.1 (폐기) | **v0.3 (확정)** |
|---|---|---|
| 교대 수를 줄여 선택했던 근무유형이 사라짐 | 자동으로 다른 값으로 교체 | **`현재 설정에서 사용할 수 없는 값`으로 표시**하고, 저장을 막고, 사용자가 다시 고르게 한다 |

유지되는 부분:
- 근무지·패턴을 바꿔 열면 화면에 남은 토글·선택값을 **전부 다시 판정**한다. 같은 근무지를 다시 열어도 마찬가지.
- 되돌리기 기록에 **데이터 신원 + 기준 버전 + 전/후 전체 상태**를 담고, 전부 일치할 때만 되돌린다. 기록 개수는 제한한다.
- 긴 목록·패널이 다른 요소를 **덮지 않는 레이아웃**으로 만든다.
- 상태 전이는 **순수 함수 한 곳에 모아** 화면과 테스트가 같은 코드를 쓰게 한다.

### 원칙 7. 늦게 도착한 응답은 버린다 — 단, "취소"는 세 가지를 구분한다 ⭐ 신설 (P10, v0.4 수정)

> Codex 2차 지적: "취소"라는 한 단어로 세 가지 다른 것을 뭉뚱그렸다. **맞는 지적이다.**

| 구분 | 뜻 | 지금 가능한가 | 화면 처리 |
|---|---|---|---|
| **① 화면 반영 취소** | 늦게 온 응답을 화면이 버림 | ✅ 가능 (창구 변경 불필요) | **버튼 없음. 내부 동작** |
| **② 기다리기 중단** | 화면이 응답을 안 기다림 | ✅ 가능하나 **뒤에서는 계속 돔** | 버튼으로 만들지 않는다 (멈춘 줄 오해) |
| **③ 작업 중단** | 시작된 내부 작업 자체를 멈춤 | ❌ **불가능. 중단 창구가 하나도 없다** | 🔴 **`[취소]` 버튼 금지** |

**확정 규칙**
- 요청마다 **순번(세대번호)** 을 붙이고, 지금 보고 있는 화면·데이터의 순번과 다르면 **응답을 버린다.**
- 같은 요청이 진행 중이면 **중복 실행하지 않는다.**
- 🔴 **실행 중 작업을 중단한다는 뜻의 `[취소]`·`[중단]` 버튼을 그리지 않는다.** 중단 창구가 없으므로 가짜 UI다.
  단 **실행 전 확인창의 `[돌아가기]`, 이탈 모달의 `[계속 편집]`/`[변경 버리고 나가기]`, 파일 선택창의 `[취소]`는 정상**이다. 금지 대상은 "이미 시작된 작업을 멈춘다"는 약속뿐이다.
- 오래 걸리는 작업 중에는 **버튼을 잠근다.**
- 실패하면 **`[다시 시도]`** 를 준다 (같은 창구를 다시 부르면 되므로 가능). 자동 무한 재시도는 하지 않는다.
- **진행 수치는 실제로 값이 오는 작업에만.** 인테이크(`34/120`)와 앱 업데이트(`62%`) 둘뿐이다. 나머지는 **`처리 중…`** 불확정 표시.
- **화면을 떠났다 돌아오면 같은 작업 상태를 복구해 보여준다.** 상태 조회 창구가 없는 작업(패턴 역추출·문서 생성·DB 교체)은 **실행 중 화면 이탈을 막는다.**

전체 근거와 작업별 판정: **`12-능력-매트릭스.md` §2·§3**

**막으려는 사고**(Codex가 지목한 "가장 먼저 깨질 지점"):
> ① 근무지 A에서 엑셀 패턴 역추출 시작 → ② 끝나기 전에 근무지 B를 엶 → ③ A의 결과가 늦게 도착해 **B 화면에 반영** → ④ 사용자는 B 설정인 줄 알고 저장 → ⑤ A에서 온 값이 섞여 저장됨

### 원칙 8. 저장 전 편집 내용을 지킨다 ⭐ 신설 (P11)

- **저장된 데이터와 편집 중 초안을 따로 관리한다.**
- 🔴 **화면에 들어가거나 데이터를 불러오는 것만으로 저장 대상이 바뀌지 않는다.** (과거 사고 원인)
- 편집한 게 있으면 **변경됨 표시**를 하고, 화면을 떠날 때 **확인**을 받는다.
- 저장 → 다시 불러오기 **왕복 검증**을 테스트로 만든다.

## 4. 화면 구조 — A안 확정

```
🏠 홈                       ← 신설
준비   근무지 관리 · 인력 관리
운영   근무표 배포 · 실적 관리(대기 건수 배지)
정산   수당 관리 · 대시보드
관리   운영 관리 · 활동 이력      ← 관리자에게만 보임
```

- 기존 메뉴 **8개 이름은 그대로** 유지하고 그룹만 씌운다.
- 🔴 **홈을 거치지 않고 각 화면에 바로 들어갈 수 있어야 한다.** 홈은 안내지 관문이 아니다.
- 홈과 대시보드의 역할 구분: **홈 = 지금 할 일 / 대시보드 = 지나간 집계·차트·순위.** (v0.8) 그래서 **수당 관리에는 추이·구성 차트를 두지 않는다** — 수당 관리 = 정규/조기 지급 요약 + 결과표 + 계산 근거 + 품의 미리보기/승인 + 문서 출력(`09` §2.2 정정).
- (v0.8) **로그인 후 셸의 상단 제목줄(56px)은 한 구성으로 통일한다**: ☰ 메뉴 접기/펼치기 · 구분선 · 화면 제목 · 역할 칩 · 계정(텍스트) · [로그아웃]. 로고·제품명 글자·[도움말]은 헤더에 없다(제품명은 좌측 메뉴 상단). 낭독 순서는 사이드바 → 헤더 → 본문 → 상태줄, 좌측 메뉴는 `주 메뉴`라는 이름을 가진 `nav`, 현재 화면 항목 표시, 본문 바로가기. 규격 정본 `11` v1.8 §C-4.

## 5. 홈 화면의 데이터 출처와 계산 규칙

> 🔴 **정본은 `12-능력-매트릭스.md` §5다.** 여기는 요약만 둔다. 충돌하면 12번 문서가 우선한다.
> v0.3에서는 창구 이름만 붙였는데, Codex가 **집계 범위·선행 조건·0건 처리·기간 범위·권한**이 없다고 지적했다. 맞는 지적이라 실제 코드를 읽어 §12에서 확정했다.

### 요약

| 막대 | 집계 단위 | 표기 예 | 핵심 선행 조건 |
|---|---|---|---|
| **준비** | 근무지 단위 (완료 근무지 / 대상 근무지) | `준비 7/10 근무지 (현재 배정 기준)` | 없음 |
| **운영** | 🔴 근무지 단위 **2단계** (합 / 대상 근무지×2) | `운영 13/20 단계` | ①이 참일 때만 ②를 평가 |
| **정산** | **월 단위** 3단계 (근무지 구분 없음 — 품의가 월 단위 데이터라서) | `월 정산 2/3 단계` | 🔴 **계산 결과가 0건이면 "승인 대기 0건"을 완료로 치지 않는다** |

#### 🔴 v0.6에서 바뀐 것 두 가지 (Codex 4차 B3)

**① 운영 막대가 4단계 → 2단계.** ③실적 유입·④승인 완료를 뺐다.
실적 데이터(`performance:list-overview`)에는 근무지 번호(`siteId`)가 없고 **이름만** 온다. 그런데 근무지 이름은 중복이 허용된다(`sites` 표에서 UNIQUE인 것은 `site_code`뿐). 같은 이름의 근무지가 둘 있으면 **경고도 없이 엉뚱한 곳에 실적이 붙는다.** 그 상태로 완료율을 만들면 **하지도 않은 일이 100%로 보인다.**
→ 근무지별 판정에는 **①근무표 생성(`siteId`)·②게시 완료(`scheduleId`)** 만 쓴다. 안정 식별자로만 판정한다.
→ 실적은 비율 대신 **건수**로 아래 별도 블록에 표시한다.

**② 준비 막대는 "현재 재직 중인 직원의 현재 배정" 기준이다.** 라벨에 반드시 적는다.
직원 조회 창구(`employees:list`)는 **지금 유효한 배치 1건**만 돌려준다. 그 달 중간에 끝난 배치를 보려면 직원마다 따로 조회해야 해서(50명이면 51회) 홈이 느려진다. **범위를 좁히고 그 사실을 화면에 밝히는 쪽**을 택했다.
→ 막대 아래 보조 문구: **"이번 달 중간에 배정이 끝난 인원은 이 숫자에 들어가지 않습니다. 월 전체 배정 이력은 인력 관리에서 확인하세요."**
→ 🔴 **조회할 때 `status: "active"`를 반드시 함께 넘긴다**(v0.6a). 안 넘기면 **퇴사자가 준비 완료 인력으로 세어진다** — 직원을 퇴사로 바꿔도 그 사람의 배정은 삭제 전까지 활성으로 남기 때문이다. 정본: `12` §5.2.2.

#### 이번 달 **대기 실적** 현황 — 비율이 아니라 건수 (v0.6 신설 / v0.6a 범위·단위 정정)

```
대기 실적 그룹 3개 · 승인 대기 실적 128건 · 재승인 필요 4건 · 확인 필요 2건
근무지 연결 불가 1개 · 중복 이름으로 연결 불확정 1개      [실적 관리에서 확인]
```

🔴 **여기에 퍼센트·완료율을 붙이지 않는다.** 분모를 확정할 수 없어서 건수로 분리한 것이다.
🔴 **`근무지 N곳`이라고 쓰지 않는다**(v0.6a). 실적 조회는 근무지 번호가 아니라 **이름 그룹**으로 묶고, 기본값이 **대기(pending) 범위**라 승인이 진행되면 숫자가 줄어든다. `근무지 N곳`이라고 쓰면 "승인할수록 유입이 줄어드는" 것처럼 읽힌다. 정본: `12` §5.3b.

- **준비 대상 근무지** = 조회 시점 현재 활성이고 삭제되지 않은 근무지. **운영 대상 근무지**(v0.5의 `운영·정산 대상 근무지`에서 개명) = 현재 활성 ∪ 이번 달 근무표가 있는 근무지. 0개면 진행 막대 대신 빈 상태.
- **문서 출력 완료** = 이력이 하나라도 있으면이 아니라, **현재 품의 승인 건에 대응하는 출력 행에 품의서·별첨1·별첨2 파일명이 셋 다** 있을 것.
- **`폴더 감시 중단됨`은 관리자에게만** 보인다(관리자 전용 창구).
- **`고아 승인행 감지`는 홈에서 뺐다.** 전용 창구가 확인되지 않았다. 실적 관리 화면 안에서만 안내한다.

🔴 **위에 없는 항목은 홈에 그리지 않는다.** 숫자를 채우기 위해 추정하지 않는다.

## 6. 표 밀도 — V3 확정, 단 "목표치"

### 6.1 계산

```
900 − 상단 제목줄 56 − 하단 전역 상태줄 32 = 본문 812px
812 − 필터바 56 − 표 머리글 40 − 위아래 여백 16 = 표 본문 700px
700 ÷ 40 = 17.5  →  약 17행
700 ÷ 32 = 21.9  →  약 21행 (좁게 모드)
```

### 6.2 ⚠️ 이 숫자는 목표치이지 확정치가 아니다 (Codex 지적 반영)

위 계산에는 아직 안 들어간 것들이 있다.

| 빠진 것 | 대략 |
|---|---|
| 가로 스크롤바 | 약 12px |
| 그룹 머리(근무지별 묶음) | 행마다 다름 |
| 윈도우 창 테두리·제목 표시줄 | 환경마다 다름 |

가로 스크롤바만 빼도 `(700−12) ÷ 40 = 17.2` → 17행, 그룹 머리가 끼면 **15~16행까지 내려갈 수 있다.**

🔴 따라서 문서·요청서에는 **"약 17행 목표, 목업과 실제 앱에서 실측"** 으로 적는다. 시안을 받은 뒤 실제로 세어 보고 확정한다.

### 6.3 표 성능은 별도 문제 (P7 표현 수정)

화면 파일이 123KB인 것은 **고치기 어렵다는 뜻**이지 **느리다는 측정 결과가 아니다.** 수천 행일 때 실제 속도는 **아직 재보지 않았다.** 개발 1단계에서 실데이터로 측정한다.

## 8. 실적 관리 화면 — 내부 3분할 ⭐ (Codex 권고 채택)

**상위 메뉴는 하나로 유지한다.** 별도 메뉴로 쪼개면 한 업무의 맥락이 끊긴다. 대신 화면 안을 3개 작업공간으로 나눈다.

| 작업공간 | 담는 것 |
|---|---|
| **① 접수·복구** | 폴더 감시 · 인테이크 진행 · 해석 실패 · 시작 복구 · **고아 승인 상태** |
| **② 승인 작업** (기본) | 승인대기 파일 · 근무지별 그룹 · 실적 표 · 행 상세 |
| **③ 재승인·비교** | 기존 승인행 ↔ 수정행 비교 · 재승인본 확정 · 관련 이력 |

- 기간·근무지 **필터는 세 작업공간에서 유지**된다.
- ①은 **정상일 때 상단 한 줄 요약으로 접히고, 오류가 있을 때만 펼쳐진다.** (세로 공간 절약 + 문제는 놓치지 않음)
- 승인 후 **다음 행으로 포커스가 예측 가능하게 이동**하고, 현재 선택·스크롤 위치가 보존된다.
- (v0.8) ② 승인 작업 표의 열은 **근무지(그룹) · 사번 · 이름 · 직급 · 근무일 · 상태 · 경고 · 구분 · 근무코드 · 시작-종료 · 시간(총=기본+연장+야간) · 시급** 순서(12칸 유지). 행 상세 패널은 표 오른쪽 360px에 붙고, 표는 810px 안에서 가로 스크롤한다 — 상세가 열린 채로도 상태·경고가 보여야 한다. 상세 패널은 표·상세에 이미 있는 항목만 그 행에서 채운다. 규격 정본 `11` v1.8 §H-2.
