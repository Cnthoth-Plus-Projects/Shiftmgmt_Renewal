## 0. 왜 이 문서가 필요한가

`가짜 UI 금지`는 원칙만으로는 지켜지지 않는다. 시안에 `[취소]` 버튼이나 `34/120` 같은 진행 수치를 그려 넣으면, 개발 단계에서 둘 중 하나가 벌어진다.

1. **동작하지 않는 버튼을 그대로 만든다** → 가짜 UI 규칙 위반
2. **시안을 맞추려고 이관 금지 영역(`main/services`·`ipc`·`preload`·`bridge`)에 새 계약을 추가한다** → 이관 금지 위반

그래서 **그리기 전에** "이 요소가 실제로 가능한가"를 확인한 표가 필요하다.

## 3. 취소 — 세 가지를 구분한다

| 구분 | 뜻 | 지금 가능한가 | 화면에 어떻게 |
|---|---|---|---|
| **① 화면 반영 취소** | 늦게 도착한 응답을 화면이 버림 | ✅ **가능.** 창구 변경 불필요. renderer 안에서 처리 | 버튼 없음. **내부 동작**(원칙 7) |
| **② 기다리기 중단** | 화면이 응답을 더 이상 기다리지 않음 | ✅ 가능하지만 **뒤에서는 계속 돈다** | 버튼으로 만들지 않는다. 만들면 "멈춘 줄" 오해 |
| **③ 작업 중단** | 이미 시작된 내부 작업 자체를 멈춤 | ❌ **불가능. 중단 창구가 하나도 없다** | 🔴 **`[취소]` 버튼을 그리지 않는다** |

### 결론 — 화면 규칙

```
✅ 오래 걸리는 작업 = 진행 표시 + 버튼 잠금
✅ 실행 전 확인창의 [돌아가기] / 이탈 모달의 [계속 편집] / 파일 선택창의 [취소]
❌ 실행 중 작업을 멈춘다는 뜻의 [취소]·[중단]   ← 중단 창구가 없음
```

**예외 없음.** 인테이크조차 중단 창구가 없다(`operations:stop-file-watch`는 폴더 감시 자체를 끄는 것이지 진행 중인 해석을 멈추는 게 아니다. 그리고 관리자 전용이다).

### 화면 이탈 시 동작

| 상황 | 처리 |
|---|---|
| 오래 걸리는 작업 중 화면을 떠남 | 내부 작업은 **계속 돈다.** 화면은 응답을 버린다(원칙 7) |
| 다시 돌아옴 | 🔴 **같은 작업의 상태를 복구해 보여줘야 한다.** "아무 일도 없었던 것처럼" 보이면 안 된다 |
| 상태 복구가 가능한 작업 | 인테이크(`performance:get-sync-state`), 시작 복구(`performance:get-startup-recovery-status`) — 조회 창구가 있음 |
| 상태 복구가 불가능한 작업 | 패턴 역추출·문서 생성·DB 교체 — 조회 창구 없음. → **실행 중에는 화면을 떠날 수 없게 잠근다** |

## 4. 권한 — 누가 무엇을 볼 수 있나

### 4.0 🔴 먼저 — 권한은 계단식이 아니다 (기존 문서의 오류 정정)

`01-product-overview.md` §5에는 **"역할 4단계. 상위 역할은 하위 역할 권한을 포함한다"** 고 적혀 있었다.
**이것은 사실과 달랐다.** `src/shared/domain/authorization.ts:11-16`을 읽어 확인했다.

> ✅ **v1.2에서 조치 완료**: `01-product-overview.md` §5 **본문을 직접 바로잡았고**, 같은 문서 §5.1에 정정 이력과 사유를 남겼다.
> (v1.1까지는 이 문서에만 정정 사실을 적어 두어 기준이 둘로 갈라져 있었다 — Codex 4차 B7 지적.)

```ts
const roleRequirementSatisfaction = {
  operator: ["operator", "planner", "reviewer", "admin"],
  planner:  ["planner", "admin"],     // ← reviewer가 없다
  reviewer: ["reviewer", "admin"],    // ← planner가 없다
  admin:    ["admin"],
};
```

**실제 구조**

```
                 admin  (전부 가능)
                /     \
        planner         reviewer     ← 서로 상하 관계가 아니다. 형제다
                \     /
                operator  (기본 권한 + 전 역할 실행 창구 — §4.2 주)
```

| 잘못 알고 있던 것 | 실제 |
|---|---|
| 승인 담당(reviewer)은 계획 담당(planner) 권한을 포함한다 | ❌ **reviewer는 직원 등록·근무지 등록·근무표 배포를 할 수 없다** |
| 계획 담당(planner)은 승인을 할 수 있다 | ❌ **planner는 실적 승인·수당 승인을 할 수 없다** |

🔴 **화면 설계에서 "승인 담당 이상"** 같은 표현을 쓰면 안 된다. **역할을 직접 열거**해야 한다.

| 근무지 쓰기 | `site-write` | **planner, admin** |
| 근무 패턴 쓰기 | `shift-pattern-write` | **planner, admin** |
| 근무표 저장·생성·배포 | `schedule-deploy` | **planner, admin** |

### 4.3 🔴 이 확인에서 드러난 설계 문제

**전역 상태줄의 `● 폴더 감시 중` 표시는 일반 사용자에게 불가능하다.**

- 폴더 감시 실행 여부는 `FileWatchStatusSnapshot.isRunning`에만 있고, 이 값은 `operations:get-file-watch-status`로만 온다 → **관리자 전용**
- `app:get-health`가 돌려주는 것은 `databaseConfigured` · `pendingDirectoryConfigured` · `approvedDirectoryConfigured` · `sessionPolicy` 뿐이다. **감시 실행 여부가 없다.**

→ v1.0 요청서의 전역 상태줄 설계는 **관리자에게만 성립한다.** 고쳐야 한다.

#### 🔴 "인테이크 상태"는 감시기 건강 상태의 대체물이 아니다

`get-sync-state.status = idle`은 **앱 시작 직후의 기본값일 수도 있다.** 감시기가 돌고 있다는 뜻이 아니다.
따라서 일반 역할에게 **초록 점 + `정상 감시 중`** 같은 표현을 쓰면 안 된다. 중립적으로 쓴다.

```
✅  최근 인테이크: 처리 이력 없음
✅  최근 인테이크: 읽는 중 34/120
✅  최근 인테이크: 해석 중
✅  최근 인테이크: 마지막 처리 완료 (14:32)      ← updatedAt/completedAt 함께
✅  최근 인테이크: 오류 1건
❌  ● 정상 감시 중                                ← 금지. 알 수 없는 사실
```

#### 🔴 "승인대기 N건"은 두 가지 다른 숫자다 — 단위를 고정한다

| 표현 | 출처 | 뜻 |
|---|---|---|
| **`대기 파일 N개`** | `performance:list-pending-files` | 아직 승인 안 된 **엑셀 파일 개수** |
| **`대기 실적 N건`** | `performance:list-overview` → `pendingCount` | 아직 승인 안 된 **실적 행 개수** |

둘 다 "승인대기 N건"으로 쓰면 같은 숫자로 오해된다. **상태줄은 `대기 파일 N개`, 홈·실적 화면은 `대기 실적 N건`.**

🔴 **결정 (v1.2)**: 안정 식별자(`siteId`) 계약이 생기기 전까지 —

1. **근무지별 운영 진행률에서 ③ 실적 유입 · ④ 승인 완료를 뺀다.** 근무지별 숫자에는 `siteId`·`scheduleId`로 판정 가능한 **①근무표 생성 · ②게시 완료만** 쓴다 (§5.3).
2. 실적은 **비율이 아니라 건수**로, `§5.3b 이번 달 대기 실적 현황`에 따로 표시한다. 여기에는 **연결 불가 N개**와 **중복 이름으로 연결 불확정 N개**를 나란히 적는다.
3. 중복 이름 판정은 `sites:list` 결과에서 같은 `name`이 2건 이상인지 세면 되므로 **계산 가능하다.** 조용히 넘어가지 않는다.

### 5.2 준비 막대 — 🔴 v1.2에서 `현재 배정 기준`으로 축소

#### 5.2.1 먼저 — v1.1의 판정을 철회한다

#### 5.2.2 🔴 확정 — 준비 막대는 "현재 배정" 기준으로 좁힌다 (사용자 결정, 2026-08-28)

Codex가 제시한 세 갈래(① N+1 수용 ② 현재 배정으로 축소 ③ 지표 보류) 중 **②를 택했다.**

이유: 홈은 앱을 열 때마다 뜨는 화면이고, ①은 직원 50명이면 조회가 **1회 → 51회**로 늘어 홈 첫 화면이 느려진다. 월 중 퇴사·이동자는 어차피 실적 엑셀 인테이크에서 잡히므로, 준비 막대가 못 보는 부분을 **라벨로 정직하게 밝히는 쪽**이 낫다.

```
분모 = 준비 대상 근무지 수 (현재 활성·미삭제)
분자 = ① 이번 달 1일에 유효한 근무 설정이 있고
       AND ② 아래 조건을 만족하는 "현재 재직 중인" 배정 인력이 1명 이상인 근무지 수
```

**② 현재 배정 판정 — 🔴 `employees:list({ siteId, status: "active" })` 1회**

`EmployeeRecord`에는 그 직원의 **최신 활성 배치**가 들어 있다(`currentSiteId` · `currentAssignmentStartDate` · `currentAssignmentEndDate` 등). 이 값으로 아래를 판정한다.

```
currentAssignmentStartDate ≤ 이번 달 말일
AND (currentAssignmentEndDate 없음 OR currentAssignmentEndDate > 이번 달 1일)
```

- 🔴 **`status: "active"`를 반드시 넘긴다 (v1.2a 추가).** 안 넘기면 **퇴사자가 준비 완료 인력으로 세어진다.**
  - `employees:list`는 직원 상태를 자동으로 걸러 주지 않는다. `query.status`를 준 경우에만 거른다(`employee-storage-service.ts:313-317`).
  - 직원을 **퇴사(`retired`)로 바꿔도 그 사람의 배정은 `active`로 남는다.** 배정을 `ended`로 닫는 것은 그 뒤 **삭제 단계**에서만 일어나고(`:615-628`), 삭제는 퇴사일이 지난 뒤에만 가능하다(`:607-613`). **그 사이 기간에는 퇴사자가 활성 배정을 그대로 갖고 있다.**
  - 따라서 조건을 안 걸면 **퇴사자만 남은 근무지가 "준비 완료"로 표시된다.**
  - `EmploymentStatus = "active" | "leave" | "retired"`(`model.ts:12`)이므로 `"active"`는 **퇴사자와 휴직자를 함께 제외**한다. 휴직자만 남은 근무지도 준비 완료로 보면 안 되므로 의도한 결과다.
- 🔴 **종료일은 배타(`>`)다.** v1.1의 `≥ 이번 달 1일`은 틀렸다. 소스(`employee-storage-service.ts:393-396`)가 `end_date IS NULL OR end_date > monthStart`로 쓰고 있고, `≥`로 하면 **8월 1일에 끝난 배치가 8월에 포함되는** 차이가 생긴다.
- 시작일 조건은 **다음 달부터 시작하는 배정을 이번 달로 세지 않기 위해** 남긴다.

**이 막대가 세는 대상을 한 문장으로**: **현재 재직 중(`active`)인 직원의, 최신 활성 배정.**

**🔴 라벨을 바꾼다 — 이 막대가 못 보는 것을 화면에 적는다**

| 보조 설명 (막대 아래 또는 도움말) | 없음 | **"이번 달 중간에 배정이 끝난 인원은 이 숫자에 들어가지 않습니다. 월 전체 배정 이력은 인력 관리에서 확인하세요."** |

이 문구가 없으면 "이 달에 일한 사람 기준"으로 읽힌다. **못 보는 범위를 밝히는 것까지가 이 지표의 일부다.**

### 5.3 운영 막대 — 🔴 v1.2에서 **2단계**로 축소 (`운영 13/20 단계`)

v1.1은 근무지 × **4단계**였다. ③ 실적 유입 · ④ 승인 완료는 `siteName` 결합에 의존하는데, 같은 이름의 근무지가 둘 있으면 **조용히 엉뚱한 곳에 붙는다**(§5.1). 잘못된 100% 완료를 만들 수 있어 **근무지별 진행률에서 뺀다.**

```
분모 = 운영 대상 근무지 수 × 2
분자 = 근무지별 완료 단계 수의 합
```

| 단계 | 완료 조건 | 결합 키 | 🔴 선행 조건 |
|---|---|---|---|
| ① 근무표 생성 | `monthly-schedules:list`에 이번 달 행 존재 | **`siteId`** | 없음 |
| ② 게시 완료 | `monthly-schedules:list-exports`에 게시 완료 이력 존재 | **`scheduleId`** | ①이 참일 때만 평가 |
| ~~③ 실적 유입~~ | — | ~~`siteName`~~ | 🔴 **제거.** §5.3b로 옮김 |
| ~~④ 승인 완료~~ | — | ~~`siteName`~~ | 🔴 **제거.** §5.3b로 옮김 |

**남은 두 단계는 전부 안정 식별자로만 판정한다.** 이름 결합이 하나도 끼지 않는다.

**선행 조건이 필요한 이유**: ①이 없는데 ②를 평가하면 "게시 이력 없음 = 미완료"가 아니라 아예 판정 대상이 아니다. 아무것도 안 한 근무지가 부분 완료로 보이면 안 된다.

🔴 **세 지표는 단위가 서로 다르다. 퍼센트만 보여주면 안 된다.** 항상 분모와 단위를 함께 쓴다.

```
✅  준비      7/10 근무지  (현재 배정 기준)
✅  운영      13/20 단계
✅  월 정산   2/3 단계
❌  준비 70%  운영 65%  정산 67%      ← 같은 종류로 오해된다
```

### 5.3b 🔴 이번 달 **대기 실적** 현황 — **비율이 아니라 건수** (v1.2 신설 / v1.2a 범위·단위 정정)

실적은 `siteId`가 없어 근무지별 완료율로 만들 수 없다. 대신 **그 자체로 참인 건수**를 그대로 보여준다. 출처는 `performance:list-overview({ scheduleMonth })` 1회 + `sites:list` 1회다.

#### 🔴 먼저 — 이 창구가 **무엇을 읽는지** (v1.2a에서 확인, Codex 5차 지적)

| 확인한 것 | 위치 | 사실 |
|---|---|---|
| `approvalScope` 기본값 | `performance-management-service.ts:642` | `query.approvalScope === "approved" ? "approved" : "pending"` — **생략하면 `pending`** |
| 읽는 대상 | 같은 파일 `:695-704`, `:722` | 선택된 보관 범위의 파일만. `pending`이면 **대기 폴더에 실제로 있는 파일만** |
| `groups`의 키 | 같은 파일 `:595-602` | `row.entry.siteName` **문자열 버킷**. 이름이 비면 `"미지정 근무지"` |
| `siteCount` | 같은 파일 `:623-628` | 결국 `groups.length`와 같은 값 |

→ 두 가지 결론:

1. **이 숫자는 "이번 달에 들어온 실적 전체"가 아니라 "아직 대기 중인 실적"이다.** 승인이 진행될수록 줄어든다. `실적이 들어온 근무지 N곳`으로 쓰면 **승인할수록 유입이 줄어드는 것처럼 보인다.**
2. **단위는 근무지 "곳"이 아니라 근무지 이름 "그룹"이다.** 같은 이름의 근무지 두 곳은 한 그룹으로 합쳐진다(§5.1과 같은 원인).

#### 확정 표시 (v1.2a)

| 표시 | 계산 | 출처 필드 |
|---|---|---|
| 🔴 **대기 실적 그룹 N개** (v1.2의 `실적이 들어온 근무지 N곳`에서 정정) | `groups.length` | `groups[]` |
| **승인 대기 실적 N건** | Σ `pendingCount` | `PerformanceOverviewSiteGroup.pendingCount` |
| **재승인 필요 N건** | Σ `needsReapprovalCount` | `needsReapprovalCount` |
| **확인 필요(경고) N건** | Σ `alertCount` | `alertCount` |
| 🔴 **근무지 연결 불가 N개** | `sites:list`의 어떤 `name`과도 안 맞는 그룹 수 | `groups[].siteName` × `sites[].name` |
| 🔴 **중복 이름으로 연결 불확정 N개** | `sites:list`에 같은 `name`이 **2건 이상** 있는 그룹 수 | 〃 |

**블록 제목도 `이번 달 대기 실적 현황`으로 한다.** 여섯 줄이 전부 대기 범위의 "아직 남은 일"이므로 블록 전체가 한 가지 뜻으로 읽힌다.

> **왜 `approved`를 같이 부르지 않는가**: 월 전체 유입을 보려면 `pending`·`approved`를 각각 부르고 합쳐야 하는데, ① 안정 ID가 없어 합칠 때 같은 이름끼리 잘못 합쳐지고, ② 두 호출 모두 파일 다시 읽기(sync)를 유발해 홈이 느려진다(`:660-686`). **홈은 "지금 할 일"을 보는 화면**이므로 대기 범위 1회로 충분하다. 월 전체 유입 집계가 필요하면 실적 관리 화면에서 범위를 골라 본다.
> **재승인과 경고를 한 줄로 합치지 않는다.** `needsReapprovalCount`(다시 승인해야 함)와 `alertCount`(확인이 필요함)는 서로 다른 필드이고 사용자가 할 일도 다르다. (Codex 5차에서 이 판단에 **이견 없음** 확인)
> 위 6개는 **모두 `PerformanceOverviewSiteGroup`에 실재하는 값**이거나 그것의 단순 합계다. 화면이 새로 계산하는 것은 없다.

🔴 **여기에 완료율·퍼센트를 붙이지 않는다.** 분모를 확정할 수 없기 때문에 이 블록을 만든 것이다.
🔴 **`근무지 N곳`이라고 쓰지 않는다.** 이름 그룹이지 근무지가 아니다.

### 5.4 정산 막대 — `월 정산 2/3 단계` (월 단위, 근무지 구분 없음)

품의 승인은 데이터 구조상 **월 단위**(`allowance_proposal_approvals.work_month`)이지 근무지 단위가 아니다.

🔴 **분모는 "월 전체 3단계"로 고정한다. 근무지 수를 곱하지 않는다.** (v1.2 재확인) 세 단계는 각각 **월 단위 레코드가 있느냐**로만 판정하므로, §5.1의 `siteName` 결합 문제와 무관하다.

| 단계 | 완료 조건 | 🔴 선행 조건 |
|---|---|---|
| ① 수당 승인 | 이번 달 계산 결과 중 미승인 = 0 | 🔴 **계산 결과가 1건 이상일 때만 평가.** 0건이면 미완료 |
| ② 품의 승인 | `allowance:list-proposal-approvals`에 이번 달 승인 행 존재 | ①이 참일 때만 |
| ③ 문서 출력 | 🔴 **그 품의 승인 행의 `export_record_id`에 대응하는 출력 이력이 있고, 그 행에 품의서·별첨1·별첨2 파일명이 셋 다 채워져 있을 것** | ②가 참일 때만 |

**③이 "이력이 하나라도 있으면 완료"가 아닌 이유**: 지난달 출력 이력이 남아 있으면 이번 달이 완료로 보인다. 현재 품의 승인 건과의 **대응 관계**를 확인해야 한다.

## 5.7 저장 전 이탈 — 실제로 막을 수 있는 범위

원칙 8(편집 초안 보호)이 적용되는 **이탈 경로 전체**와, 보호 코드를 고치지 않고 막을 수 있는지.

| 이탈 경로 | 화면 안에서 막을 수 있나 | 처리 |
|---|---|---|
| 좌측 메뉴로 다른 화면 이동 | ✅ 가능 (화면 내부 라우팅) | 이탈 확인 모달 |
| **같은 화면에서 다른 근무지 선택** | ✅ 가능 | 이탈 확인 모달 |
| 마법사 단계 뒤로 가기 | ✅ 가능 | 단계 안에서는 초안 유지, 마법사 자체를 나갈 때만 확인 |
| **로그아웃** | ✅ 가능 (화면이 먼저 처리) | 이탈 확인 모달 |
| **창 닫기 / 앱 종료** | ⚠️ **미확인 — 🔴 파일럿 범위 밖** | Electron 창 종료를 화면이 가로채려면 main 쪽 처리가 필요할 수 있다. 그곳은 이관 금지 영역이다. **확인 시점은 아래 확정 참조** |
| 앱 강제 종료·전원 차단 | ❌ 불가능 | 막을 수 없다. 설계에서 제외 |

#### 🔴 확정 (v1.2 / v1.2a에서 등식 제거) — 확인 시점은 **구현 착수 전**

v1.1은 "**파일럿 전에 확인한다**"고 적었는데, 파일럿은 시안·화면 검증 단계라 창 종료 처리를 확인할 필요가 없다. 문구와 실제 범위가 어긋나 있었다(Codex 4차 B8).

v1.2에서는 "**구현 착수 전 = 설계 LOCK 전**"이라고 적었는데, 이러면 **이 확인이 끝나기 전에는 설계를 LOCK할 수 없다**는 게이트가 생긴다(Codex 5차 지적). 그건 의도가 아니었다. **등식을 지운다.**

| 항목 | 확정 |
|---|---|
| 확인 시점 | 🔴 **구현 착수 전**(= `08-rebuild-plan.md` 1단계 뼈대 작업 시작 전). **설계 LOCK의 선행 조건이 아니다.** 설계 LOCK은 이 확인 없이 진행한다 |
| 파일럿 범위 | ❌ **비범위.** 파일럿의 화면·시나리오·수용 기준 어디에서도 창 닫기 차단을 **제공한다고 표현하지 않는다** |
| 파일럿에서 막는 이탈 경로 | 라우트 이동 · 같은 화면 내 근무지 전환 · 마법사 닫기 · 로그아웃 **4개뿐** |
| 확인 전까지의 가정 | 🔴 **마법사에서 편집 중 창을 닫으면 내용이 사라진다고 가정한다** |

시안에는 이탈 확인 모달을 그리되, 그 모달이 **창 닫기에도 뜬다고 약속하지 않는다.**

**v1.2a에서 여기까지는 확인했다 (읽기 전용):**

| 확인한 것 | 결과 |
|---|---|
| main 프로세스에 창 종료를 가로채는 처리가 있는가 | ❌ **없다.** `src/main/main.ts`에 `BrowserWindow`의 `close` 이벤트 처리도 `preventDefault`도 없다. `app.on("window-all-closed")`(`:306-309`)는 **닫힌 뒤** 정리 작업만 한다 |
| 그래서 지금 상태에서 창을 닫으면 | **막히지 않고 그냥 닫힌다.** 편집 중이던 내용은 사라진다 |
| 화면 쪽(renderer)만으로 막을 수 있는가 | ⚠️ **미확인.** 후보는 있으나(브라우저 표준 이탈 경고) **이 앱에서 실제로 동작하는지 띄워서 확인하지 않았다.** 확인 전에는 "된다"고 쓰지 않는다 |

→ 결론은 그대로다. **파일럿에서 창 닫기 차단을 약속하지 않는다.**
