### 5.1 R1의 정확한 표 계약

아래 DDL 의미를 그대로 구현한다. 외래키를 새로 추가하지 않는다.

```sql
CREATE TABLE IF NOT EXISTS employee_employment_periods (
  id TEXT PRIMARY KEY,
  employee_id TEXT NOT NULL,
  start_date TEXT NOT NULL,
  end_date TEXT,
  closure_provenance_complete INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT,
  CHECK (end_date IS NULL OR end_date >= start_date)
);
CREATE INDEX IF NOT EXISTS idx_employee_employment_periods_employee
  ON employee_employment_periods (employee_id, start_date ASC);
CREATE UNIQUE INDEX IF NOT EXISTS idx_employee_employment_periods_open
  ON employee_employment_periods (employee_id) WHERE end_date IS NULL;

CREATE TABLE IF NOT EXISTS employee_retirement_history_closures (
  id TEXT PRIMARY KEY,
  employment_period_id TEXT NOT NULL,
  history_kind TEXT NOT NULL,
  history_id TEXT NOT NULL,
  previous_status TEXT,
  previous_end_date TEXT,
  created_at TEXT NOT NULL,
  UNIQUE (employment_period_id, history_kind, history_id)
);
CREATE INDEX IF NOT EXISTS idx_employee_retirement_closures_period
  ON employee_retirement_history_closures (employment_period_id, history_kind);

CREATE TABLE IF NOT EXISTS employee_employment_period_events (
  id TEXT PRIMARY KEY,
  employee_id TEXT NOT NULL,
  employment_period_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  event_date TEXT NOT NULL,
  previous_event_date TEXT,
  reason TEXT,
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_employee_employment_events_employee
  ON employee_employment_period_events (employee_id, created_at DESC);

CREATE TABLE IF NOT EXISTS wage_rate_history (
  id TEXT PRIMARY KEY,
  wage_rate_id TEXT NOT NULL,
  employee_id TEXT NOT NULL,
  employment_period_id TEXT,
  employee_code TEXT,
  employee_name TEXT,
  action_type TEXT NOT NULL,
  hourly_rate REAL NOT NULL,
  effective_from TEXT NOT NULL,
  effective_to TEXT,
  wage_reason TEXT,
  change_reason TEXT NOT NULL,
  actor_user_id TEXT NOT NULL,
  actor_login_id TEXT NOT NULL,
  actor_display_name TEXT NOT NULL,
  actor_role TEXT NOT NULL,
  occurred_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_wage_rate_history_wage_rate_id
  ON wage_rate_history (wage_rate_id, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_wage_rate_history_employee_id
  ON wage_rate_history (employee_id, occurred_at DESC);
```

### 5.2 R2의 정확한 컬럼·인덱스 계약

### 5.3 R3·R4의 정확한 백필 계약

- 기간 id: `'legacy:' || employees.id`.
- `start_date=hire_date`, `end_date=retire_date`.
- `closure_provenance_complete`: `status='retired'`면 0, 아니면 1.
- `created_at/updated_at`: 직원 행의 같은 값.
- 직원별 기존 기간이 하나라도 있으면 합성하지 않는다.
- v0.5.8 원문보다 안전하게 `hire_date IS NOT NULL AND TRIM(hire_date) <> ''`를 모두 요구한다.
- 배정 연결: 같은 직원, `period.start_date <= assignment.start_date`, `start_date DESC, created_at DESC` 첫 행.
- 시급 연결: 같은 직원, `period.start_date <= wage.effective_from`, 같은 정렬 첫 행.
- 연결 UPDATE는 현재 `employment_period_id IS NULL`인 행에만 적용한다.

### 6.3 최소 변경 원칙

- 요구사항과 직접 연결되지 않은 정리·이름 변경·포맷 변경을 하지 않는다.
- 기존 호출 계약과 타입을 유지한다. 계약 변경이 필요해 보이면 구현하지 말고 반환한다.
- 파일 전체 재생성 대신 필요한 hunk만 바꾼다.
- 테스트를 구현에 맞춰 약화하지 않고, 구현이 기존·신규 계약을 만족하게 한다.
- `package.json`/lockfile을 바꾸지 않는다. Node 24의 `node:sqlite`, `node:fs`, `node:crypto`, `node:os`, `node:path`만으로 verifier를 만든다.

## 7. 적용할 불변조건과 과거 함정

### 7.1 이번 작업의 필수 불변조건

- 운영 데이터는 원본을 덮어쓰지 않고 별도 임시 경로에서 검증한다.
- 데이터 이관은 표 수만 맞추지 않고 행·컬럼 값까지 검증한다.
- 퇴직/재입사 이력의 `closure_provenance_complete=0` 의미를 1로 바꾸지 않는다.
- 시급·승인·감사 이력은 삭제하거나 재계산하지 않는다.
- `app_setting_entries`만 현행 환경 경로 변환 예외이며, 나머지 39표는 canonical row content가 입력 JSON과 같아야 한다.

### 7.2 반드시 피할 과거 실패

- v0.5.8에는 V4의 `shift_pattern_duty_types` DDL이 없다. 파일 전체 복사 시 V4 스키마가 회귀한다.
- `restoredTableCount`는 전체 표 수가 아니라 **비어 있지 않아 insert한 표 수**다. 현재 입력 기준 성공값은 40이 아니라 32다.
- 원본 JSON은 33개 표가 비어 있지 않지만 `app_setting_entries`는 현행 변환 대상이다. 일반 복원 count는 32이고 target settings는 17행이다.
- 입력 총 3,599행과 target 총행은 settings 18→17 변환 때문에 같지 않다. 현행 정책 유지 시 target은 3,598행이다.
- v0.5.8 백필의 `hire_date IS NOT NULL`만 복사하면 레거시 빈 문자열 입사일로 잘못된 기간을 만든다. `TRIM(...) <> ''` 음성 시험이 필수다.
- 성공 경로만 확인하지 말고 known table/column exclusion warning 0과 future unknown column skip을 동시에 검증한다.
- SHA·행 수·시험 수는 명령 출력에서 그대로 보고한다. 추정값을 쓰지 않는다.

## 8. 착수 전 확인

아래가 하나라도 다르면 제품 파일을 수정하지 않고 `BLOCKED`로 회신한다.

1. 저장소·브랜치·baseline commit이 머리말과 일치한다.
2. 초기 `git status --short`가 빈 출력이다.
3. §4.1의 기존 5파일 SHA가 §3.4와 일치하며 새 script 경로는 아직 없다.
4. `package.json`과 lockfile SHA가 §3.4와 일치한다.
5. 운영 JSON SHA가 `EFEC...DB9`이며 읽기 가능하다.
6. 요구사항·코드 전략·검증 기준 사이 모순이 없다.

### 9.4 실제 운영 JSON 검증기

build 후 아래 명령을 실행한다.

```powershell
node scripts/verify-v3-json-migration.mjs --input "C:\Users\pangyo\AppData\Roaming\shiftmgmt-v3-4\data\backups\json\shiftmgmt-backup-20260917-194251.json" --expected-sha EFEC1F0EF364E6CA4D88DBBCF8D52E88FFDC2EAC452E258CA7D09B4BDDE28DB9 --expected-tables 40 --expected-rows 3599
```

스크립트는 최소한 다음을 스스로 assert하고 요약 출력한다.

- 입력 SHA/표/행: 위 기대값과 일치하고 실행 전후 SHA 동일.
- preview와 실복원 모두 네 표·세 컬럼에 대한 exclusion warning 0.
- target schema table set: 입력과 정확히 같은 40/40. V4의 `shift_pattern_duty_types`와 네 신규 표를 모두 포함.
- `restoredTableCount=32`.
- target 총행 `3,598`; source `app_setting_entries=18`, target `17`, 기존 경로 설정 유지 warning 1개.
- `app_setting_entries`를 제외한 39표: 표별 행 수와 canonicalized row content hash가 입력과 정확히 동일.
- 신규 표 행 수: `87 / 0 / 0 / 0`.
- 신규 컬럼 비NULL: 배정 `87/89`, 시급 `84/87`, snapshot `0/37`.
- target `PRAGMA quick_check='ok'`와 `PRAGMA integrity_check='ok'`.
- 실제 복원은 `mkdtemp`로 만든 고유 임시 userData/SQLite만 사용하고 `finally`에서 자신이 만든 디렉터리만 정리.

canonical 비교는 객체 key를 정렬하고 각 표의 행을 canonical JSON 문자열 기준으로 정렬해 DB 반환 순서에 의존하지 않는다. `app_setting_entries` 차이는 숨기지 말고 유일한 정책 예외로 별도 출력한다.

## 10. 성공 조건

- [ ] R1~R9 전부 구현 위치와 실행 증거가 있다.
- [ ] 네 표, 세 컬럼, 여덟 인덱스가 exact contract로 존재한다.
- [ ] migration 재실행은 멱등이고 NULL/blank/공백 입사일은 기간을 만들지 않는다.
- [ ] sentinel 왕복에서 네 표·세 컬럼 값이 전부 보존되고 known exclusion 경고가 0이다.
- [ ] 실제 운영 JSON verifier가 §9.4 전 항목으로 RC 0이다.
- [ ] 정적 검사·빌드·전체 시험·smoke·map·release check가 통과한다.
- [ ] 변경 파일 집합이 §4.1과 정확히 일치하고 새 의존성/생성물 변화가 없다.
- [ ] 보호 경로와 운영 JSON SHA가 불변이다.
- [ ] 한 개 구현 commit 뒤 저장소가 clean이다.
- [ ] 아래 회신 양식에 재현 가능한 전체 증거가 있다.

## 11. 즉시 중단 조건

- 지시·소스·테스트가 서로 충돌한다.
- 허용 목록 밖 파일이나 새 의존성 변경 없이는 구현할 수 없다.
- 기준 commit, 초기 status, 보호 SHA, 입력 JSON SHA가 다르다.
- API·DB 의미·설정 변환·아키텍처 결정을 새로 해야 한다.
- 시험을 약화하거나 fallback/placeholder를 넣어야만 통과한다.
- verifier가 운영 SQLite를 열어야 하거나 입력 JSON을 변경해야 한다.
- 검증 환경 또는 필수 도구가 없어 성공 조건을 확인할 수 없다.
