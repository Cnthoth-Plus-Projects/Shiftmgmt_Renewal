- 1개: 그 한 행만 제거.
- 2개 이상: 모호한 삭제 오류를 throw하고 전체 복원/preview를 실패시킨다.
- performance entry를 먼저 삭제한 뒤 모호성을 발견하는 흐름이어도 같은 transaction rollback으로 원상복구되어야 한다.

### P2-6-D4 — 파일 메타데이터를 일반적으로 잘못 덮어쓴다 (BLOCKER)

증거:

`database-migration-service.ts`의 현재 갱신:

- `entry_count = remainingEntries.length`
- `approved_entry_count = remainingEntries.length`
- `warning_count = 0`

이 구현은:

- 남은 미승인 행을 승인된 것으로 만든다.
- Pool/BP/기존 비지급 행을 payable entry count에 넣을 수 있다.
- 삭제 대상과 무관한 경고까지 지운다.

교정:

- `entry_count`: 남은 지급 가능 실적 기준. 공유 도메인 게이트와 같은 의미를 사용한다.
- `approved_entry_count`: 삭제 후보는 연결 승인 없음이 선행 조건이므로 다른 행의 실제 승인 수를 보존/정확히 재계산한다. 절대 남은 전체 행 수로 설정하지 않는다.
- `warning_count`: 삭제한 행의 `alert_json`에 귀속되는 경고만 제거하고 다른 파일/행 경고는 보존한다. 절대 무조건 0으로 설정하지 않는다.
- `row_count`, `file_size`는 유지한다.
- 실제 운영 파일 기대는 그대로:
  - row_count 5
  - file_size 5
  - entry_count 4
  - approved_entry_count 4
  - warning_count 0
  - preview 4행

필수 추가 시험:

- 한 파일에 정상 승인 1행, 정상 미승인 1행, Pool 또는 기존 비지급 1행, 무사번 삭제 대상 1행이 함께 있는 fixture
- 삭제 대상 alert 1개와 무관한 정상 행 warning 1개
- 정리 후 payable entry count, approved count, warning count가 각각 실제 의미와 일치
- 무관한 warning이 사라지지 않음

## 9. release:check 정정

1차 HANDOFF가 “Gemini는 commit하지 않는다”와 `npm run release:check RC 0`를 동시에 요구한 것은 Sol 패킷의 모순이었다. 현재 `release-check.mjs`는 제품 변경이 남아 있으면 `작업 트리 깨끗` 항목 때문에 반드시 실패한다.

이번 교정에서:

- Gemini는 commit하지 않는다.
- `npm run release:check RC 0`는 Gemini 완료 조건에서 제외한다.
- 대신 §8의 typecheck/lint/full test/build를 각각 통과시킨다.
- Sol이 구현을 수락하고 정상 commit 지점을 만든 뒤 clean worktree에서 release check를 실행한다.

이 프로세스 정정 때문에 제품 코드나 release script를 수정하지 않는다.
