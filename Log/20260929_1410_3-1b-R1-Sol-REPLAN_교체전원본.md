## 2. 차단 결함 R31-RACE-06 — 변경 성공 뒤 재확인 대기 중 두 번째 비밀번호 변경 요청 가능

`src/web/screens/login.ts:507`은 첫 `changePassword` 성공 직후 공용 `isSubmitting`을 `false`로 푼다. `:511-514`에서 `checking`으로 전이하지만 `renderL4:339`는 초기 확인 시 오류 문구가 비어 있어 변경 폼을 계속 보여준다. 폼 규칙 검사에서 새 입력을 채우면 변경 버튼이 다시 활성화된다. 따라서 첫 세션 조회가 아직 끝나지 않았는데 변경 요청을 재전송할 수 있다. 이는 발송 지시의 R31-RACE-03과 “변경 재호출 금지”에 어긋난다.

Sol이 **실제 설치 Chrome 154**에서 별도 임시 시험 데이터 폴더를 사용해 재현했다. 관리자 계정과 무관한 시험용 운영자 계정으로 실제 L1→L4 로그인 후 비밀번호 변경을 1회 성공시켰다. 첫 `auth:get-session` 요청만 네트워크에서 보류하고 L4를 확인했다. 첫 변경 후에도 L4 입력 폼이 보였고, 새 유효 입력을 채운 뒤 변경 버튼이 활성화됐다. 버튼을 누르자 `auth:change-password` 요청이 총 **2회** 관측됐다. 변경 결과나 시험 자격증명 값은 출력·기록하지 않았다.

재현 출력: `{"firstSessionHeld":true,"l4FormVisible":true,"secondSubmitEnabled":true,"changePasswordCalls":2,"duplicateRequestSent":true}`. 이는 테스트 스텁으로 변경 API를 성공시킨 결과가 아니라 실제 서버의 첫 변경을 수행한 뒤 **세션 조회 응답만** 지연한 결과다. 검증 서버 PID 37372의 명령줄·18740 포트 소유를 확인하고 해당 PID만 종료했으며 포트 해제를 확인했다. 기존 격리 시험 폴더를 재사용했고 새 데이터 폴더를 만들지 않았다.
