# 2. 발주 차단 문제

## BLOCKER 1 — `되돌리기`와 forward-only의 충돌이 닫히지 않았습니다

정본 `07-invariants-and-pitfalls.md:16-23`은 다음을 요구합니다.

> 승인된 계산 결과를 이력 없이 덮어쓰지 않는다. 과거 판정 스냅샷을 보존한다.

하지만 실제 `returnApprovedPerformanceFileToPending`은 다음을 수행합니다.

- `allowance_calculation_items`와 `allowance_calculations`를 `DELETE`
- `performance_approvals`도 삭제
- 테스트도 기존 승인 이력과 계산 결과가 각각 **0건**이 되는 것을 명시적으로 확인
  (`performance-approval-flow-service.test.ts:782-788`)

`access-log`에는 `승인완료 → 승인대기 되돌리기`라는 일반 문자열만 남습니다. 삭제된 승인 스냅샷·계산 금액·정책 버전은 남지 않으며, 이 로그 기록도 삭제 트랜잭션이 끝난 뒤 별도로 수행됩니다.

따라서 다음 논리는 성립하지 않습니다.

```text
기능이 실제로 존재함 + 실행 로그가 남음
→ forward-only 위반이 아님
```

**고칠 것**

- v2의 “규칙 2 위반 아님” 단정을 삭제하고 **LOCK ↔ 이관 코드 충돌**로 공개하세요.
- 둘 중 하나를 발주 전에 결정해야 합니다.
  1. 승인·계산을 삭제하지 않고 취소/무효 이력으로 보존하도록 구현 계약을 고친다.
  2. 품의 승인 전의 명시적 되돌리기를 forward-only의 예외로 인정한다고 LOCK에 근거와 범위를 기록한다.
- 2번을 택하더라도 현재 access log만으로는 삭제된 계산을 재현할 수 없다는 잔여 위험을 적어야 합니다.

소스 수정은 이번 교차검증 범위가 아니므로 수행하지 않았습니다.

## BLOCKER 2 — `숨긴 행 포함해서 보기`는 현재 가짜 UI입니다

v2 970줄은 `숨긴 행 포함해서 보기` 체크 상자를 요구합니다. 현재 계약에는 이를 지원하는 경로가 없습니다.

- `PerformanceOverviewQuery`에는 `approvalScope`, `forceReparse`, `section`, `scheduleMonth`만 있고 `includeHidden`이 없음
- `listPerformanceOverview`는 숨김 승인 ID를 읽어 762~767줄에서 **무조건 제외**
- preload/IPC에 숨김 목록 조회·숨김 해제·숨김 포함 조회 채널이 없음
- visibility service의 숨김 전체 삭제 함수는 테스트 초기화 전용뿐임

따라서 체크 상자를 그리면 눌러도 구현할 수 없는 동작이 됩니다.

또한 v2의 “차단 사유 다섯 가지”도 정확한 공개 계약이 아닙니다. 화면 row가 미리 받는 값은 `canHideApprovedRow`와 `hideApprovedRowBlockedReason`이고, 실제 action service에는 별도의 런타임 실패까지 있습니다. 고정된 다섯 문장을 UI가 자체 판정하게 하지 말아야 합니다.

**고칠 것**

- 다음 중 하나를 발주 전에 확정하세요.
  1. `includeHidden`/숨김 목록·복원 계약을 구현 범위로 정식 추가한 뒤 체크 상자를 유지한다.
  2. 이관 코드 불변을 유지한다면 체크 상자를 삭제하고, 숨김 기능 자체를 이번 파일럿에서 보류하거나 현재의 비가역적 목록 제외임을 정직하게 명시한다.
- 비활성 여부와 사유는 `PerformanceOverviewRow.canHideApprovedRow` / `hideApprovedRowBlockedReason`을 정본으로 쓰고, action 실패 메시지는 실행 오류로 별도 표시하세요.

## BLOCKER 3 — `수당` 열의 출처를 추적 대상에서 빼면 안 됩니다

v2 269줄의 현재 처리는 불충분합니다.

```text
열은 그대로 둔다
출처는 미정이다
§5-1 동작 정의표에서는 뺀다
```

확인 결과:

- `PerformanceOverviewRow`에는 수당 금액이 없음 (`performance-file.ts:320-345`)
- 다만 `performance:get-comparison`은 승인 행의
  `approvedCalculation.snapshot.totalAllowanceAmount`를 반환할 수 있음
  (`performance-management-service.ts:786-823`)
- 이는 선택한 행의 비교/상세용 계약이지, 수천 행 overview 표의 금액 열을 한 번에 채우는 계약은 아님

즉 “소스 전체에 값이 없다”도 정확하지 않고, “출처를 정하지 않은 채 표에 둔다”도 맞지 않습니다.

**권고안**

- 이관 코드 불변을 유지한다면 overview 표에서는 `수당` 열을 빼고, 승인 행 상세/비교 패널에서만 `performance:get-comparison.approvedCalculation.snapshot.totalAllowanceAmount`로 보여 주세요.
- 표 열을 반드시 유지하려면 `PerformanceOverviewRow`에 금액과 미계산 상태를 포함하는 계약 변경을 먼저 승인해야 합니다.
- 어느 쪽이든 `11-디자인-요청서.md:633`을 함께 정정해 LOCK과 소스를 다시 맞춰야 합니다. v2에서만 예외로 덮고 출처 검증을 면제하면 안 됩니다.

# 3. Codex께 물은 3가지에 대한 답

## 1) 정정 판정이 맞는가

**부분적으로 맞습니다.** 채널 존재 여부 정정은 대부분 맞지만, `되돌리기`의 forward-only 준수 결론과 숨김 행 복원 가능성은 틀렸습니다. `기존 설정 복사`도 “근무 패턴 목록 조회 가능” 범위로 좁혀야 합니다.

## 2) `수당` 열의 현재 처리가 맞는가

**아닙니다.** 열을 유지하면서 출처 추적에서 빼는 것은 가짜 UI 금지와 추적성 원칙을 모두 약화합니다. 위 권고안처럼 **overview에서 제거하고 상세로 이동**하거나, 공개 계약 변경을 먼저 확정해야 합니다.

## 3) 빠뜨린 것이 있는가

새로 확인한 발주 차단 사항은 위 3건입니다. 추가로 다음 표현을 바로잡아야 합니다.

- “오판 5건”이라고 했지만 표와 정정 기록은 `되돌리기·행 숨김·복구·패턴 추출·기존 설정 복사·고객사`의 **6개 주장**을 다룹니다. 이슈 묶음 기준인지 개별 주장 기준인지 숫자를 명확히 하세요.
- `countcheck.js`는 구조 수치를 출력하는 도구이며 의미 계약의 정확성까지 검증하지는 않습니다. “14항목 수치 일치”로 표현하면 맞지만, 전체 내용 검증 통과 근거로 쓰면 안 됩니다.
