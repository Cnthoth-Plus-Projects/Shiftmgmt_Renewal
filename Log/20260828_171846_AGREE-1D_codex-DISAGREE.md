## 3. B2 수정 요구 — 권한 표는 실제 래퍼와 채널 수를 그대로 반영

`12-능력-매트릭스.md:154`의 다음 묶음 표기는 수정해야 한다.

- `app:*`는 일괄 `withSession`이 아니다. `register-core-handlers.ts:105-182`의 버전·헬스·업데이트 핸들러는 해당 래퍼 없이 등록된다.
- `auth:*`도 일괄 `withSession`이 아니다. 로그인·세션 조회·복구·비밀번호 변경은 채널별 등록 방식이 다르며, 로그인은 구조상 세션 선행을 요구할 수 없다.
- `access-logs:record`는 `register-core-handlers.ts:379-380`에서 `withSession`이 맞다.
- `operations:*`는 등록 문자열 기준 고유 채널이 40개다. `34개`를 유지하지 말고 실제 목록에서 다시 집계한다.

권장 수정 방식은 `app:*`와 `auth:*`를 한 행으로 포괄하지 않고, 세션/역할 검증 여부가 같은 채널끼리만 묶는 것이다. `전체 111개`와 영역별 합계도 다시 합산해 서로 일치시킨다.

## 4. B3 수정 요구 — 홈 진행률 정의

### 4.1 과거 배치는 `employees:list({siteId})` 1회로 계산할 수 없음

현재 문서의 “N+1 호출 없이 해당 월 배치 인원을 계산 가능” 판정은 철회해야 한다.

소스 근거:

- `src/shared/bridge/contracts.ts:347-351`의 공개 `EmployeeListQuery`에는 `siteId`, `status`, `keyword`만 있다. 월 또는 `includeHistoricalAssignments`를 전달할 수 없다.
- `src/main/services/employee-storage-service.ts:267-290`은 기본값에서 `latest_assignments.status = 'active'`인 최신 배치만 선택한다.
- 같은 파일 `:317`의 `siteId` 필터도 `currentSiteId`에만 적용된다.
- 월 중 종료된 과거 배치를 조회하는 내부 함수 `listStoredEmployeesForSiteMonth`는 존재하지만 renderer bridge에 노출되지 않았다.
- 공개 계약만 사용하면 `employees:list()` 후 직원별 `employees:list-assignments(employeeId)`로 배치 이력을 조회하는 방식이 필요하다. 이는 N+1 호출이다.
- 기간 겹침 조건은 소스의 배타적 종료일 의미를 따라 `startDate <= monthEnd && (endDate 없음 || endDate > monthStart)`로 맞춘다. 현재 문서의 `endDate >= monthStart`는 월 첫날 종료 배치를 포함시키는 차이가 있다.

보호 코드와 bridge 계약을 바꾸지 않는 조건에서는 다음 중 하나를 선택해야 한다.

1. 파일럿 데이터 규모에서 N+1을 명시적으로 수용하고 로딩·실패 상태를 설계한다.
2. 준비 진행률을 현재 활성 배치 기준으로 축소하고 라벨을 그렇게 바꾼다.
3. 정확한 월 배치 집계용 bridge가 제공될 때까지 월 이력 기반 지표를 보류한다.

### 4.2 `siteName` 경고만으로 단계 ③·④를 유지할 수 없음

`PerformanceOverviewSiteGroup`은 `src/shared/domain/performance-file.ts:347-357`처럼 `siteName`만 제공하고 `siteId`를 제공하지 않는다. 또한 `sites` 테이블은 `site_code`만 UNIQUE이며 `name`은 UNIQUE가 아니다(`sqlite-storage-service.ts:43-49`).

따라서 현재 방식은 다음 두 문제를 해결하지 못한다.

- 이름이 일치하지 않는 그룹뿐 아니라 **동일 이름 근무지가 둘 이상인 경우**에도 조용히 잘못 연결될 수 있다.
- 연결 불명 상태를 운영 `26/40 단계`의 분자·분모에 일관되게 넣을 수 없다. 분자에서만 제외하면 사실상 미완료이고, 분모에서도 빼면 완료율이 부풀 수 있다.

결정: 안정 식별자 계약이 없는 현재 파일럿에서는 근무지별 운영 진행률에서 단계 ③ `실적 수신`, ④ `검토 완료`를 제거한다. 근무지별 숫자에는 `siteId`/`scheduleId`로 판정 가능한 ① `근무표 생성`, ② `게시 완료`만 사용한다.

성과는 별도 월간 현황으로 표시한다.

- 실적 유입 그룹 N개
- 승인 대기 실적 N건
- 재승인/경고 N건
- 근무지 연결 불가 N개
- 중복 이름으로 연결 불확정 N개

`운영·정산 대상 근무지`라는 명칭도 `운영 대상 근무지`로 정리한다. 월 정산 3단계는 근무지별 분모가 아니라 월간 계산·제안·확정 레코드 상태로 유지한다.

## 5. 질문에 대한 답변

### Q1. 권한 오류는 `01-product-overview.md`도 수정해야 하는가?

**반드시 수정해야 한다.** `01-product-overview.md:4`는 설계 전에 먼저 읽는 현재 기준 문서이고, `:117`의 “상위 역할은 하위 역할 권한을 포함한다”는 실제 권한 모델과 다르다. `planner`와 `reviewer`는 상하 관계가 아닌 형제 역할이고 `admin`만 전체 권한을 가진다.

12번 문서에 정정 사실만 적으면 두 개의 기준이 공존한다. 01의 본문을 바로잡고 변경 이력에 정정 사유를 남긴다.

### Q2. `siteName` 불일치 경고로 충분한가?

**충분하지 않다.** 불일치 경고는 “일치하지 않음”만 드러낼 뿐 중복 이름의 오연결을 막지 못한다. 안정 식별자가 추가되기 전에는 근무지별 운영 진행률에서 단계 ③·④를 제거하고 별도 월간 성과 현황으로 분리한다.

### Q3. 창 닫기 차단을 확인하지 않고 파일럿을 진행할 수 있는가?

**가능하다.** 단, 파일럿 화면·시나리오·수용 기준 어디에서도 창 닫기 차단을 제공한다고 표현하지 않는다. 현재 `12`의 “파일럿 전에 확인” 문구는 다음 중 하나로 정합화한다.

- 실제로 파일럿 전에 확인한다.
- 또는 “구현 착수/설계 LOCK 전에 확인”으로 바꾸고 파일럿 비범위임을 유지한다.

### Q4. 가장 큰 잔여 위험은 무엇인가?

홈 진행률의 **정확해 보이는 오판정**이다. 과거 배치 누락과 `siteName` 중복/불일치 때문에 실제 운영 상태와 다른 완료율을 표시할 수 있다. 일반적인 빈 상태보다 위험하며, 사용자가 잘못된 완료 판단을 내리게 한다.

### Q5. 절대 규칙 위반이 남아 있는가?

다음은 수정 전까지 절대 규칙 위반으로 본다.

- 공개 계약으로 불가능한 월 배치 1회 조회를 “소스 확인 완료”로 확정한 것
- 실제 세션 래퍼와 다른 권한 매트릭스를 확정 사실로 표시한 것
- 첫 진입 문서인 01에 잘못된 역할 상속을 유지한 것
- 중복 가능한 `siteName`을 조용히 안정 식별자처럼 사용해 정밀 진행률을 만드는 것

보호 코드·스키마 수정, 게시/전송 수행, 실제 운영 입력 등의 새 위반은 확인하지 않았다.
