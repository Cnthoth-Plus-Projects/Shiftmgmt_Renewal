## 추가 판정

### 1. 원칙 7·8이 P10·P11을 막는가

**원칙 8은 충분한 방향이다. 원칙 7은 절반만 막는다.**

원칙 7은 다음 세 개를 구분해야 한다.

1. **화면 반영 취소** — 세대번호가 다른 늦은 응답을 renderer에서 버림. 현재 창구 변경 없이 가능하다.
2. **호출 대기 취소** — 화면이 응답을 더 이상 기다리지 않음. `ipcRenderer.invoke`의 백엔드 작업이 실제로 멈춘다는 뜻은 아니다.
3. **업무 작업 중단** — DB 교체·품의 문서 생성처럼 main 프로세스에서 이미 시작된 작업 자체를 중단. 전용 중단 창구와 안전한 롤백 보장이 있을 때만 가능하다.

`04-api-contract.md`에는 `performance:get-sync-state`라는 인테이크 진행 조회는 있지만, `shift-patterns:analyze-import`, `allowance:approve-proposal`, `operations:update-database-from-migration`의 취소 창구와 수치 진행률 창구가 없다. 따라서 다음처럼 고쳐야 한다.

- 모든 장기 작업에 `[취소]`와 `N/M`을 강제하지 않는다.
- 실제 진행 수치가 있는 작업만 `34/120`을 표시한다.
- 수치가 없으면 `처리 중…` 같은 불확정 진행 표시를 쓴다.
- 전용 취소 기능이 확인된 작업에만 `[중단]`을 둔다.
- 승인·DB 교체처럼 실행 후 중단이 안전하지 않은 작업은 버튼을 잠그고 전역 작업 상태에서 완료/실패를 추적한다.
- 화면을 떠나도 백엔드 작업이 계속된다면 다시 돌아왔을 때 동일 작업 상태를 복구해 보여줘야 한다.

원칙 8에는 NICE-TO-HAVE로 앱 창 닫기·로그아웃·다른 근무지 전환도 동일한 dirty 이탈 경로를 타게 한다는 문구를 추가하면 된다.

### 2. 홈 계산 규칙에 남은 가짜 UI 위험

**남아 있다. `고아 승인행`을 확인 전 숨기는 규칙은 적절하지만, 나머지 진행 막대도 아직 확정 계산으로 보기 어렵다.**

필수로 정해야 할 것:

- **집계 단위**: 운영 4단계와 정산 3단계가 전체 앱 기준인지, 근무지별 단계의 합인지 불명확하다. 활성 근무지가 10개면 분모를 `10×4`로 할지, 모든 근무지가 끝나야 단계 1개를 완료로 볼지 정해야 한다.
- **선행 조건**: 실적 0건인데 승인 대기 0건이면 운영 ④를 완료로 표시하면 안 된다. ③ 실적 유입이 완료된 뒤에만 ④를 평가해야 한다.
- **정산의 공집합 처리**: 계산 결과가 0건인데 수당 승인 대기 0건이라는 이유로 정산 ①을 완료 처리하면 안 된다.
- **기간·대상 범위**: `이번 달`의 기준일, 비활성 근무지, 월 중 신규·종료 근무지, 조기 지급 건 포함 여부를 정해야 한다.
- **문서 출력 완료**: 단순히 문서 출력 이력이 하나 있는지, 현재 품의 승인에 대응하는 품의서·별첨1·별첨2 세 파일이 모두 있는지 정의해야 한다.
- **권한**: 홈은 operator도 보지만 폴더 감시 조회·재시작은 `04`에서 관리자 전용 `operations:*`에 속한다. 일반 사용자에게 `[다시 시작]`을 그리면 눌러도 실행할 수 없다. 일반 역할은 `[원인 보기]` 또는 권한 설명, 관리자만 `[다시 시작]`이어야 한다.

또한 문서 스스로 창구 반환값을 “개발 1단계에서 확인”한다고 적었다. 홈이 1차 파일럿이라면 필요한 반환값·권한을 **파일럿 의뢰 전에 읽기 전용으로 확인**해야 한다. 확인할 수 없는 진행 막대는 파일럿에서 제거하거나 `데이터 출처 검증 대기`로 설계 대상에서 제외해야 한다.

### 3. 확인창 4종 분리의 실효성

**실효성이 있다.** 종류 수보다 “언제 확인창을 띄우지 않는가”와 빨강의 범위를 제한한 것이 확인 피로를 줄인다.

다만 구현은 네 개의 서로 다른 모달을 복제하지 말고 하나의 공통 모달에 `단순/위험/파괴/사유` 변형을 두는 방식이 좋다. `10` 원칙 2 제목의 3종 표기는 4종으로 고쳐야 한다.

### 4. 파일럿 3장 선정 타당성 / 껍데기 검증 충분성

**세 화면 선정은 타당하다. 껍데기 검증은 부분적으로만 충분하다.**

- 홈: 새 정보구조와 메뉴 그룹 검증
- 실적: 최고 데이터 밀도·표·상태·승인 검증
- 마법사: 복잡한 편집 상태·이탈·패널 겹침 검증

껍데기는 세 파일에 반복해서 넣는 것만으로는 역할별 메뉴와 상태줄 오류 상태를 검증하지 못한다. 파일 수를 늘릴 필요는 없고 세 파일에 역할을 나눠 주면 된다.

- 홈: operator — 관리자 메뉴 미노출, 감시 문제는 원인 보기만
- 실적: reviewer — 승인 가능, 상태줄 정상/오류 상태
- 마법사: planner — 편집 가능, 승인 버튼은 권한 설명과 함께 비활성

키보드 검증을 파일럿의 성공 조건으로 유지하려면 최소 JavaScript로 다음을 실제 동작시켜야 한다.

- 메뉴·탭 이동과 보이는 포커스
- 실적 표 ↑↓/Space/Enter
- 모달 열기·포커스 가둠·Esc·원래 위치 복귀
- `aria-disabled` 버튼의 포커스와 이유 낭독

시각 시안만 받을 목적이라면 “키보드 검증”이라는 표현을 “키보드 상태 설계 검수”로 낮추고, 실제 동작 검증은 구현 단계로 분리해야 한다.

### 5. 여전히 남은 가장 큰 위험

**화면이 기존 내부 창구보다 더 많은 능력을 약속하는 것**이다.

대표 사례는 모든 장기 작업에 붙인 `[취소]`, 모든 진행 상태의 `N/M`, 일반 사용자의 폴더 감시 `[다시 시작]`, 아직 반환값을 확인하지 않은 홈 진행률이다. 이 상태로 시안을 확정하면 구현 단계에서 다음 둘 중 하나가 발생한다.

1. 동작하지 않는 버튼·수치를 그대로 만들어 가짜 UI 규칙을 위반한다.
2. 시안을 맞추기 위해 이관 금지 영역의 API·서비스 계약을 수정한다.

따라서 **디자인 요소별로 `데이터 출처 / 실행 창구 / 허용 역할 / 취소 가능 여부 / 수치 진행률 가능 여부`를 한 표로 확정하는 능력 매트릭스**가 파일럿 전 필요하다.

### 6. 절대 규칙 위반 여부

현재 문서 상태에는 다음 위반 가능성이 남아 있다.

1. **가짜 UI 금지**
   - 중단 창구 없는 작업의 `[취소]`
   - 진행 수치가 없는 작업의 `N/M`
   - 반환값·집계 규칙을 확인하지 않은 홈 진행률
   - 권한 없는 사용자의 폴더 감시 `[다시 시작]`

2. **이관 코드 수정 금지 위험**
   - 위 UI를 실제 동작시키기 위해 `main/services`, `ipc`, `preload`, `bridge`에 새 취소·진행 계약을 추가하면 금지 영역을 건드리게 된다.

자동 교체, DB 스키마, 직접 실적 입력, forward-only, 승인·계산 트랜잭션, 엑셀 정렬, 게시 절차에 관한 새 위반은 발견하지 못했다.

   - 작업별 `진행 수치 있음/없음`, `안전한 중단 가능/불가`, `화면 이탈 시 동작`, `재진입 복구`, `허용 역할`을 명시한다.
   - 실제 창구가 없는 `[취소]`·`N/M` 요구를 제거한다.

2. **홈 계산 규칙 완성 및 창구 사전 확인**
   - 근무지별 집계 방식, 선행 조건, 0건 처리, 기간 범위, 문서 3종 대응 관계를 정의한다.
   - 홈 파일럿 의뢰 전에 필요한 반환값과 권한을 확인한다.

3. **접근성 대비 수정**
   - 배지 글자 4.5:1과 테두리·아이콘 3:1을 분리한다.
   - `#B15C00/#FDF3E4`, `#6B7280/#F4F5F7` 조합을 4.5:1 이상으로 조정한다.
   - 포커스 링도 인접 색 대비 3:1 기준을 명시한다.

4. **파일럿 검증 가능하게 수정**
   - 키보드 검증을 할 거면 최소 상호작용 JavaScript를 필수로 한다.
   - 정적 시안만 받을 거면 키보드 동작 검증을 구현 단계로 분리한다.
   - 2차 의뢰 전 나머지 10개 화면의 화면×상태 인벤토리를 요청서에 추가한다.

5. **문서 정합성 수정**
   - `10`의 `사용자 재결정 필요/남은 결정`을 확정 상태와 맞춘다.
   - 원칙 2 제목의 `3종`을 `4종`으로 고친다.

## 고치면 좋은 것(NICE-TO-HAVE)

- 가상 표에 `aria-rowcount`, `aria-rowindex` 또는 동등한 전체 행/현재 위치 전달 기준을 구체화한다.
- 진행률은 매 건마다 낭독하지 말고 주요 구간·완료·실패만 알리거나 `progressbar` 의미를 사용한다.
- 빈 활성 근무지 0개일 때 준비 진행률을 0%로 오해시키지 말고 별도 빈 상태로 처리한다.
- 앱 닫기·로그아웃·다른 근무지 전환도 원칙 8의 동일한 dirty 이탈 경로를 타게 한다.
- 세 파일럿에 operator/reviewer/planner 역할을 나눠 껍데기 권한 상태를 함께 검증한다.
