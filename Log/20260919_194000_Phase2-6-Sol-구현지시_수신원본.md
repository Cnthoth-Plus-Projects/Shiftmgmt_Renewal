## 7. 상세 요구사항

### R1. 공유 도메인 지급 대상 게이트

`src/shared/domain/performance-file.ts`에 모든 진입점이 사용할 수 있는 명시적인 정규 게이트를 둔다.

권장 개념:

- `isNonPayablePerformanceEntry`
- `isPayablePerformanceEntry`
- 필요하면 비지급 이유를 반환하는 별도 helper

기존 `isNonPayableSubstitutePerformanceEntry`는 대무 전용 의미를 유지해도 된다. 다만 승인·계산·관리 서비스가 전역 비지급 판정에 이 대무 전용 helper만 사용하면 안 된다.

어떤 실적이든 다음 중 하나면 비지급이다.

- Pool 직원
- 표시 이름의 `(P)` 표식으로 Pool임을 알 수 있는 경우
- BP 표시 이름
- `employeeCode.trim()`이 빈 값
- 기존 규칙상 비지급 대무

비지급 이유는 가능한 한 서로 구분한다.

- Pool
- BP
- 사번 없음
- 기존 대무 비지급 사유

기존 공개 helper 이름을 호환 alias로 남길 수 있으나, V4 서비스의 승인·계산 관련 call site는 새 정규 게이트를 명시적으로 사용해야 한다.

### R2. 신규 실적 수집과 파서

`schedule-return-performance-parser.ts`와 수집·저장 경로에 다음을 적용한다.

- BP는 기존처럼 실적 후보에서 제외한다.
- Pool은 실적 이력으로 보존할 수 있지만 법정공휴일·연장·휴일 등 모든 업무 유형에서 비지급으로 표시한다.
- Pool 판단은 직원이 과거 어느 시점엔가 Pool이었다는 이유가 아니라 해당 `work_date`에 유효한 팀/배치로 판단한다.
- 이름의 `(P)` 표식은 section과 무관하게 Pool로 인정한다.
- Pool 실적에는 사번·임금 누락을 지급 오류로 만들지 말고 Pool 비지급 사유를 남긴다.
- 파싱된 비-BP 실적 중 `employeeCode.trim()`이 빈 행은 preview/conflict 확정 전에 제거한다.
- 제거 사실은 파일 단위 경고로 집계하며 개인정보인 이름을 경고에 나열하지 않는다.
- 여러 행이 제거돼도 행별 중복 경고 대신 개수 중심의 안정된 경고를 사용한다.

경계 조건:

- 과거에는 Pool이었지만 해당 근무일에는 일반 팀에 정상 배치되고 사번이 있는 직원은 다른 지급 조건을 만족하면 대상이 될 수 있어야 한다.
- 현재 Pool이라는 이유만으로 과거 일반 팀 근무까지 일괄 비지급 처리하면 안 된다.

### R3. 승인·관리·수당 계산 경로

다음 모든 경로가 R1의 정규 게이트를 사용해야 한다.

- allowance approval
- performance approval flow
- performance management
- approved allowance calculation
- performance file intake/storage 중 승인 가능성 또는 집계 판단

요구 동작:

- Pool, BP, 무사번 비-BP는 새 승인 대상이 되지 않는다.
- 위 대상은 새 수당 계산을 만들지 않는다.
- batch와 단건 동작이 같아야 한다.
- UI에서 우회 호출하거나 이미 저장된 실적을 직접 선택해도 서비스 계층에서 차단해야 한다.
- 기존 확정 계산 행은 이번 변경으로 삭제·재계산하지 않는다.
- 반환 결과나 오류/skip 사유는 호출자가 비지급 원인을 파악할 수 있는 현재 구조의 가장 자연스러운 방식으로 제공한다.

### R4. Access 가져오기

기존 BP skip을 유지한다.

무사번 비-BP 행은 다음처럼 처리한다.

- 가져온 수당 금액이 없거나 0이면: 실적을 만들지 않고 skip count와 집계 경고를 남긴다.
- 양수의 가져온 수당 금액이 있으면: 금전 데이터 손실을 숨기지 말고 전체 작업을 명시적으로 실패시킨다.
- 실패 시 부분 반영이 남지 않아야 한다.

### R5. V3 JSON 복원 시 target-only 정리

`database-migration-service.ts`의 V3 JSON 복원에서 모든 테이블 적재 후, 같은 `BEGIN` 트랜잭션 안에서, `COMMIT` 전에 무사번 비-BP 실적을 점검한다.

삭제 전 각 후보에 대해 직접 연결 및 논리 연결을 모두 확인한다.

- approval
- hidden row
- direct calculation
- approval을 통해 연결되는 calculation

하나라도 연결돼 있으면:

- 삭제하지 않는다.
- 전체 복원을 예외로 실패시킨다.
- 현재 트랜잭션을 롤백한다.
- 기존 target DB의 sentinel 데이터가 그대로 남아야 한다.

연결이 전혀 없으면:

- target DB에서만 해당 performance entry를 제거한다.
- 원본 JSON과 V3 DB는 수정하지 않는다.
- 연결된 performance file preview에서 동일 행을 보수적으로 제거한다.
- preview 매칭 기준은 최소한 employee name + work date를 포함해야 한다.
- 정확히 1개면 제거한다.
- 0개면 preview에 원래 없던 것으로 보고 계속할 수 있다.
- 2개 이상이면 모호한 삭제로 판단해 전체 복원을 실패·롤백한다.
- `entry_count`는 남은 대상 행 기준으로 다시 계산한다.
- `approved_entry_count`는 실제 남은 승인 가능/승인 행과 모순되지 않게 유지한다.
- `warning_count`는 정리된 preview를 기준으로 다시 계산한다.
- 원본 파일 fingerprint 의미인 `row_count`와 `file_size`는 변경하지 않는다.

실제 입력에는 정확히 다음 경고를 1회 추가한다.

`백업 JSON의 사번 없는 실적 1건을 V4 복원 대상에서 제거했습니다. 원본 백업은 변경하지 않았습니다.`

복원 결과의 imported performance count는 원본 개수가 아니라 실제 target 저장 개수 349건을 보고해야 한다.

### R6. 실제 검증기

`scripts/verify-v3-json-migration.mjs`는 broad exclusion으로 차이를 숨기면 안 된다. 명시적으로 허용한 변환만 정규화한다.

실제 입력 기대:

- source: 40 tables / 3,599 rows
- target: 3,597 rows
  - 기존 `app_setting` 변환 차이 1건
  - 이번 무사번 performance entry 제거 1건
- target `performance_entries`: 349건
- target 무사번 비-BP performance entry: 0건
- Pool performance entry: 44건 보존
- Pool approval: 0건
- Pool calculation: 0건
- calculation: 263건 / 56,076,024원 유지
- allowance-approved calculation: 64건 / 13,611,839원 유지
- preview warning과 restore warning 각각 정확히 2건:
  - 기존 settings 관련 경고
  - 이번 무사번 정리 경고

비교 정책:

- `app_setting`: 기존 승인된 변환만 허용
- `performance_entries`: source에서 정확히 위 무사번 행 1건만 제외
- `performance_files`: 위 파일에서 명시한 필드와 preview 차이만 허용
- 그 밖의 모든 테이블: 원본과 동등해야 함

검증기는 다음도 유지·검증한다.

- `PRAGMA quick_check`
- `PRAGMA integrity_check`
- 성공·실패 양쪽 임시 디렉터리 정리
- 복원 정리 오류 aggregation
- 잘못된 expected rows와 SHA mismatch에서 nonzero exit

### R7. overview ghost 제거

현재 overview에서 승인된 것으로 보일 수 있는 ghost 2건은 다음 원인이다.

- Pool 법정공휴일 1건
- 무사번 비-BP 법정공휴일 1건

이번 작업에서는 승인 디렉터리 구조 자체를 재설계하지 않는다. 공유 게이트로 Pool을 비지급 처리하고 target-only 정리로 무사번 행을 제거해, 실제 복원 결과에서 알려진 ghost가 0건이 되게 한다.

## 8. 구현 지침

1. 먼저 기준 hash/bytes와 clean worktree를 확인한다.
2. 공유 도메인 게이트와 단위 테스트를 먼저 만든다.
3. 각 서비스의 기존 개별 판정을 정규 게이트로 교체한다.
4. 파서의 work-date-specific Pool 판정을 구현한다.
5. Access 및 JSON 복원 정책을 각각 구현한다.
6. JSON 정리는 반드시 기존 복원 트랜잭션 내부의 commit 전 단계에 둔다.
7. 검증기의 허용 차이를 좁고 명시적으로 모델링한다.
8. 실제 사용자 입력 검증은 temp target으로만 수행한다.
9. 구현 중 기존 승인 계산을 재계산해야 할 것처럼 보이면 중단한다. 이는 요구사항 위반 신호다.

## 9. 필수 테스트

최소한 아래 신규 회귀 사례를 자동 테스트로 추가한다. 서로 다른 의미의 검증을 하나의 과도한 테스트로 합치지 않는다.

### 9.1 공유 도메인

- Pool은 업무 유형과 무관하게 비지급
- BP는 비지급
- 무사번 비-BP는 비지급

### 9.2 파서

- Pool의 법정공휴일/연장/휴일 유형이 비지급이며 missing wage 지급 오류를 만들지 않음
- 무사번 비-BP 행이 preview/conflict 확정 전에 제거되고 집계 경고가 남음
- 과거 Pool 배치가 종료되고 근무일 기준 일반 팀인 정상 사번 직원은 Pool로 오판되지 않음

### 9.3 승인·관리·계산

- 승인 flow에서 Pool/BP/무사번이 단건과 batch 모두 차단됨
- performance management에서 직접 선택 우회가 차단됨
- approved calculation이 제외 대상을 계산하지 않음

### 9.4 마이그레이션

- JSON의 연결 없는 무사번 행 1건이 target에서만 제거되고 file metadata/preview/count가 기대값이 됨
- approval/hidden/calculation/direct-or-logical link가 있으면 복원이 실패·롤백됨
- Access 무사번·무금액 행은 skip+warning
- Access 무사번·양수 금액 행은 실패·롤백

기준 86개 집중 테스트에 최소 14개의 의미 있는 신규 사례가 추가되는 것을 기대한다. 개수가 다르더라도 위 의미가 모두 독립적으로 증명되면 회신에서 차이를 설명한다.

## 11. 필수 negative 검증

## 13. 즉시 중단 조건

다음 중 하나면 임의 판단으로 계속하지 말고 `HANDOFF.md`에 BLOCKED 또는 DRIFT로 회신한다.

- 기준 commit, branch, clean 상태 불일치
- 허용 파일의 기준 hash/bytes 불일치
- 스키마 변경이 필요함
- 기존 승인 계산을 삭제·재계산해야만 구현 가능함
- 무사번 행의 financial/history link를 안전하게 판정할 수 없음
- preview 행을 유일하게 식별할 수 없어 2개 이상 후보가 일치함
- V3 또는 원본 백업에 쓰기가 필요함
- 허용 파일 밖의 제품 코드 변경이 필요함
- 실제 입력 검증에서 알려진 금액/개수 불변식이 깨짐

## 14. Gemini 회신 형식

구현을 완료한 뒤 이 파일 전체를 아래 구조의 결과 보고서로 교체한다. 채팅만으로 회신하지 않는다.

1. Status: `IMPLEMENTED`, `BLOCKED`, 또는 `DRIFT`
2. 시작 branch/commit/clean 상태
3. 수정 파일 목록과 각 파일의 변경 목적
4. 공유 게이트 및 각 진입점 적용 요약
5. JSON/Access 정리와 rollback 구현 요약
6. 추가 테스트 목록
7. 모든 검증 명령별 RC와 핵심 출력
8. 실제 입력 검증 수치
9. negative 검증별 결과
10. 입력 JSON 검증 전후 SHA-256/bytes
11. temp directory 검증 전후 count
12. 최종 `git status --short`
13. 최종 diff 요약과 남은 위험
14. 생성한 commit이 있다면 commit hash. 임의 commit은 만들지 않는 것을 기본으로 한다.

테스트를 실행하지 못했거나 결과가 기대값과 다르면 성공으로 표현하지 않는다.
